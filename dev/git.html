Разработка и применение программного обеспечения в физических исследованиях

Git

Git — распределённая система контроля версий (version control system, VCS): хранит историю изменений файлов, откатывается к любой прошлой версии и объединяет работу нескольких человек над одним проектом. Для научной работы Git так же обязателен, как Python или LaTeX.

Зачем физику контроль версий

Курсовая с расчётами:

processing.py
processing_new.py
processing_final.py
processing_final_v2.py
thesis_final_v2_FINAL(2).py
thesis_final_v2_FINAL(2)_fixed_mass.py

Через месяц нужно перегенерировать третий рисунок для статьи, и никто, включая тебя, не помнит, каким из файлов он построен. А «финальная» версия даёт другой хвост распределения, потому что константа, поправленная по дороге, вылетела из головы.

Контроль версий закрывает три проблемы:

  • История вместо зоопарка файлов. В проекте лежит один processing.py, а все его прошлые версии остаются в Git. К любой можно вернуться, любые две сравнить построчно.
  • Воспроизводимость расчётов. Каждое состояние проекта имеет уникальный идентификатор, хеш коммита. Запиши его рядом с результатом, и через год ты дословно восстановишь код, посчитавший график. «Рисунок 3 построен на коммите a3f2c17» и есть воспроизводимость.
  • Совместная работа. Когда над обработкой данных работают три человека, Git объединяет их изменения и показывает, кто, что и зачем поменял. Пересылать архивы code_v7_new.zip по почте не нужно.

Репозиторий на сервере служит и резервной копией: запушил вечером, и умерший диск ноутбука перестал быть катастрофой.

Как устроен Git

Устройство Git держится на трёх идеях, из которых выводится почти всё поведение команд.

Снимки, а не различия

Git хранит не «патчи к предыдущей версии», а снимки (snapshots). Каждый коммит — фотография всего проекта в момент фиксации плюс метаданные: автор, дата, сообщение и ссылка на родительский коммит. Неизменившиеся файлы не копируются, Git ссылается на уже сохранённые объекты, и репозиторий не разбухает.

Каждый объект адресуется хешем SHA-1, строкой вида a3f2c17b... из git log; в командах достаточно первых 6–8 символов.

Три состояния

Файлы проекта живут в трёх зонах:

рабочая директория  ──►  индекс (staging area)  ──►  репозиторий (.git)
  правишь файлы          git add: отбираешь           git commit:
                         изменения для коммита        фиксируешь снимок
  • Рабочая директория (working directory) содержит обычные файлы, которые ты редактируешь.
  • Индекс (staging area) — «предбанник» коммита. Командой git add ты складываешь сюда изменения, которые войдут в следующий снимок.
  • Репозиторий живёт в скрытой папке .git, хранящей все коммиты. Коммит, до которого не дотянуться ни веткой, ни тегом, держится ещё около месяца записью в git reflog, а потом вычищается сборщиком мусора, так что спасательный приём из шпаргалки в конце главы работает не бесконечно.

Индекс кажется лишним, пока не понадобится закоммитить часть накопленных правок: исправление формулы одним коммитом, эксперименты с графиками — другим.

Коммиты образуют граф

Каждый коммит ссылается на родителя, поэтому история образует направленный ациклический граф (DAG). Пока работаешь один, он вырождается в цепочку; ветки заставляют его ветвиться, слияния — сходиться.

A ─── B ─── C ─────── F      main
       └── D ─── E ───┘      fft-filter

Ветка — подвижный указатель на коммит, файл на 41 байт внутри .git; копии проекта не создаётся, поэтому ветки заводятся мгновенно и бесплатно. HEAD указывает на место в графе, где ты сейчас находишься.

Базовый цикл работы

Разовая настройка

# представься: имя и почта попадут в каждый твой коммит
git config --global user.name "Lev Landau"
git config --global user.email "l.landau@g.nsu.ru"

# называть главную ветку main, как принято на GitHub
git config --global init.defaultBranch main

Создать или склонировать репозиторий

# превратить текущую папку в репозиторий (появится скрытая папка .git)
git init

# или склонировать существующий проект с сервера
git clone https://github.com/nsu-phys/beam-dynamics.git

Правки → индекс → коммит

В петле, описанной ниже, проходит почти вся повседневная работа.

git status                  # что изменилось? (спрашивай постоянно)

git add processing.py       # добавить файл в индекс
git add plots/              # можно папку целиком
git add -p                  # интерактивно, по кускам — очень полезно

git commit -m "Учтена поправка на температуру датчика"

git status                  # убедиться, что всё зафиксировано

git status показывает состояние всех трёх зон и подсказывает следующий шаг. Первое время вызывай её до и после каждой операции.

Смотрим историю и различия

git log                     # полная история с авторами и датами
git log --oneline           # по строчке на коммит
git log --oneline --graph --all   # весь граф с ветками, псевдографикой

git diff                    # что поменялось, но ещё не добавлено в индекс
git diff --staged           # что уже в индексе и войдёт в коммит
git diff a3f2c17 HEAD -- processing.py  # как файл изменился со старого коммита

git show a3f2c17            # что именно сделал этот коммит

.gitignore: что не должно попасть в репозиторий

Git отслеживает только явно добавленные файлы, но git status перечисляет всё подряд, от кешей Python до гигабайтных файлов с данными. Файл .gitignore в корне проекта говорит, что игнорировать. Заготовка для научного проекта:

# байткод и кеши Python
__pycache__/
*.pyc
.ipynb_checkpoints/

# виртуальное окружение
.venv/

# данные измерений и результаты расчётов — им не место в git
data/
*.h5
*.root
*.npz

# тяжёлые артефакты: чекпойнты моделей, дампы
checkpoints/
*.ckpt

# мусор редакторов и ОС
.idea/
.vscode/
.DS_Store

# LaTeX-мусор
*.aux
*.synctex.gz

В репозитории живёт написанное руками (код, тексты, конфиги) и не живёт измеренное на установке или сгенерированное расчётом. Сам .gitignore коммитится: правила исключений общие для всей группы.

Ветки

Ветка позволяет экспериментировать, не трогая работающий код: хочешь попробовать другой алгоритм фильтрации сигнала, не комментируй полфайла, а заведи ветку, названную по сути эксперимента.

git branch                    # список веток, звёздочка — текущая
git switch -c fft-filter      # создать ветку и переключиться на неё
# ...правишь и коммитишь сколько угодно...
git switch main               # вернуться на main: файлы мгновенно
                              # станут такими, какими были там

git switch появился в Git 2.23; в старых руководствах то же самое делают git checkout -b fft-filter и git checkout main.

Слияние

Когда эксперимент в ветке удался, влей её обратно:

git switch main
git merge fft-filter          # влить коммиты fft-filter в main
git branch -d fft-filter      # удалить ненужный больше указатель

Если main с момента ветвления не менялся, Git передвинет указатель вперёд (fast-forward). Если менялся, появится коммит слияния с двумя родителями, и граф из картинки выше сходится в одну линию.

Конфликты

Если в двух ветках изменены одни и те же строки, Git откажется выбирать за тебя и вставит в файл маркеры, размечающие обе версии:

<<<<<<< HEAD
dt = 1e-12  # шаг интегрирования для жёсткой задачи
=======
dt = 5e-12  # компромисс между точностью и скоростью
>>>>>>> fft-filter

Конфликт — не поломка, а вопрос. Отредактируй файл, оставив правильный вариант или скомбинировав оба, удали маркеры и заверши слияние:

git add integrator.py         # пометить конфликт разрешённым
git commit                    # завершить merge

Если решил не сливать, вместо этих двух команд нужна одна:

git merge --abort             # откатить слияние целиком

После git commit сливать уже нечего, и git merge --abort ответит, что отменять нечего.

Чем мельче коммиты и чем чаще ты сливаешь ветки, тем реже и безобиднее конфликты.

Удалённые репозитории

Пока коммиты лежат только на твоём ноутбуке, нет ни резервной копии, ни совместной работы. Удалённый репозиторий (remote) хранит копию проекта на GitHub, GitLab или на институтской машине группы.

git remote -v                  # список удалённых репозиториев
# после git clone там уже есть origin — адрес, откуда клонировал

# привязать локальный репозиторий к созданному на GitHub
git remote add origin git@github.com:username/beam-dynamics.git

git push -u origin main        # отправить ветку main на сервер;
                               # -u запоминает связку, дальше просто git push

git fetch                      # скачать чужие коммиты, НЕ трогая твои файлы
git pull                       # fetch + merge: скачать и влить в текущую ветку
git push                       # отправить свои коммиты

git fetch безопасен всегда: он лишь обновляет локальное знание о сервере, после чего можно посмотреть git log origin/main и разобрать коммиты коллег. git pull объединяет fetch с немедленным слиянием. Типовой ритм: сел за работу, сделай git pull, закончил, сделай git push. Чем чаще синхронизируешься, тем меньше конфликтов.

Fork + pull request

В чужой репозиторий, будь то библиотека вроде numpy или проект соседней лаборатории, напрямую пушить нельзя. Стандартный механизм:

  1. Fork. Кнопкой на GitHub делаешь личную копию репозитория в своём аккаунте.
  2. Клонируешь свой форк, создаёшь ветку, коммитишь исправление.
  3. Пушишь ветку в свой форк.
  4. Открываешь pull request (PR) — предложение «заберите мои коммиты к себе» с описанием и дифом.
  5. Владельцы читают код, пишут замечания (code review), ты дополняешь ветку новыми коммитами, и PR обновляется автоматически.
  6. Одобренный PR вливают в основной репозиторий.

Так живёт весь open source и заметная часть открытой науки; исправление одной строки в документации scipy проходит тот же путь. Внутри своей группы обычно пушат в общий репозиторий, но правки всё равно оформляют ветками и PR ради ревью.

Хорошие практики

Держи коммиты атомарными, по одному логическому изменению на коммит. «Исправлена нормировка спектра» и «добавлен скрипт карты магнитного поля» — два коммита, а не один «изменил всякое». Атомарный коммит можно понять, откатить или перенести целиком, коммит-свалку нельзя. По той же причине старайся, чтобы проект в каждом коммите хотя бы запускался: тогда любая точка истории годится для поиска момента, где всё сломалось.

Столько же значит сообщение. Слово fix не говорит, что починили, где и почему; через полгода git log из fix, fix2 и wip превращается в археологические раскопки на вечер. Диф и так покажет, что поменялось. Пиши короткий заголовок с сутью изменения, не «поменял коэффициент», а «Увеличен шаг сетки: старый не влезал в память на кластере». По общепринятому соглашению заголовок укладывают в 50 символов и не растягивают дальше 72. Сообщение должно объяснять, зачем.

Git создан для текста и плохо переносит большие бинарники. Каждый попавший в историю гигабайт останется в ней навсегда, и клонирование станет невыносимым. Сырые данные с установки, HDF5/ROOT-файлы, видео, обученные модели в репозиторий не кладут. Для версионирования больших файлов рядом с кодом существуют Git LFS (в git хранятся лишь ссылки, а содержимое лежит на отдельном сервере) и DVC (Data Version Control, версионирующий данные и пайплайны обработки, а сами файлы складывающий в любое хранилище, хоть в облако, хоть на сетевой диск группы). Никогда не коммить пароли, токены и ключи: вычистить секрет из истории почти невозможно, а клоны коллег успевают разойтись.

Если что-то пошло не так

Закоммиченное почти невозможно потерять: Git скорее сохранит лишнее, чем удалит нужное. Шпаргалка по типовым ситуациям:

СитуацияКоманда
Испортил файл, хочу версию из последнего коммитаgit restore file.py (незакоммиченные правки исчезнут!)
Сделал git add лишнегоgit restore --staged file.py (убирает из индекса, правки останутся)
Опечатка в сообщении последнего коммита или забыл файлgit commit --amend (только пока не запушил)
Хочу «рассыпать» последний коммит обратно в правкиgit reset --soft HEAD~1 (коммит исчез, изменения остались в индексе)
Выкинуть последний коммит вместе с изменениямиgit reset --hard HEAD~1 (опасно, правки будут уничтожены)
Отменить уже запушенный коммитgit revert a3f2c17 (новый коммит с обратным изменением, история не переписывается)
Срочно нужна другая ветка, а правки не законченыgit stash прячет изменения, git stash pop возвращает
«Я всё сломал, коммиты пропали»git reflog, журнал последних положений HEAD; найди нужный хеш и вернись командой git reset --hard <хеш>

git reset --hard — одна из немногих команд, молча и непоправимо уничтожающих незакоммиченную работу. Прежде чем её набирать, сделай git status и убедись, что терять нечего. Историю переписывает и git rebase, переносящий коммиты ветки поверх другой так, будто они там и делались: граф выходит линейным и читаемым, но у перенесённых коммитов новые хеши, то есть прежних коммитов больше нет. Не переписывай историю (reset, --amend, rebase) в ветках, уже запушенных на сервер и подхваченных коллегами: им придётся разгребать разъехавшийся граф.
