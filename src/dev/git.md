# Git

Git — это распределённая система контроля версий (version control system, VCS), запоминающая историю изменений твоих файлов, умеющая откатываться к любой прошлой версии и объединять работу нескольких человек над одним проектом. Для современной научной работы Git так же обязателен, как Python или LaTeX, и в данной главе мы разберём его от базового цикла до команд, спасающих в безнадёжных ситуациях.

## Зачем физику контроль версий

История, знакомая каждому, кто писал курсовую с расчётами:

```text
processing.py
processing_new.py
processing_final.py
processing_final_v2.py
thesis_final_v2_FINAL(2).py
thesis_final_v2_FINAL(2)_fixed_mass.py
```

Через месяц нужно перегенерировать третий рисунок для статьи, и выясняется, что никто, включая тебя, не помнит, каким из перечисленных файлов он построен. А «финальная» версия почему-то даёт другой хвост распределения, потому что константа, поправленная тобой по дороге, тут же вылетела из головы.

Контроль версий закрывает сразу три проблемы, хорошо знакомые любому расчётчику:

*   **История вместо зоопарка файлов.** В проекте лежит один `processing.py`, а все его прошлые версии, сохранённые в Git, остаются под рукой. К любой можно вернуться, а любые две сравнить построчно.
*   **Воспроизводимость расчётов.** Каждое состояние проекта имеет уникальный идентификатор, называемый хешем коммита. Достаточно записать его рядом с полученным результатом, и через год ты дословно восстановишь код, посчитавший график. Фраза «Рисунок 3 построен на коммите `a3f2c17`» и есть воспроизводимость.
*   **Совместная работа.** Когда над обработкой данных работают три человека из научной группы, Git аккуратно объединяет внесённые ими изменения и показывает, кто, что и зачем поменял. Пересылать архивы `code_v7_new.zip` по почте больше не нужно.

Есть и побочная выгода, поскольку репозиторий, заведённый на сервере, служит ещё и резервной копией. Запушил вечером, и умерший диск ноутбука перестал быть научной катастрофой.

## Как устроен Git

Устройство Git держится на трёх идеях, и дальше почти всё поведение команд выводится из перечисленных ниже правил.

### Снимки, а не различия

Git хранит не «патчи к предыдущей версии», а **снимки** (snapshots). Каждый коммит представляет собой фотографию всего проекта, сделанную в момент фиксации, плюс метаданные: автор, дата, сообщение и ссылка на родительский коммит. Неизменившиеся файлы при этом не копируются, потому что Git ссылается на уже сохранённые объекты, и репозиторий не разбухает.

Каждый объект адресуется неповторимым хешем SHA-1, а это те самые строки вида `a3f2c17b...`, выводимые в `git log`, причём в командах достаточно первых 6–8 символов, взятых от начала хеша.

### Три состояния

Файлы проекта живут в трёх зонах, показанных на схеме:

```text
рабочая директория  ──►  индекс (staging area)  ──►  репозиторий (.git)
  правишь файлы          git add: отбираешь           git commit:
                         изменения для коммита        фиксируешь снимок
```

*   **Рабочая директория (working directory)** содержит обычные файлы, которые ты редактируешь.
*   **Индекс (staging area)** играет роль «предбанника» коммита. Командой `git add` ты складываешь сюда изменения, которые войдут в следующий снимок.
*   **Репозиторий** живёт в скрытой папке `.git`, хранящей все зафиксированные коммиты. Коммит, до которого больше не дотянуться ни веткой, ни тегом, держится ещё около месяца записью в `git reflog`, а потом вычищается сборщиком мусора, так что спасательный приём из шпаргалки в конце главы работает не бесконечно.

Промежуточный индекс кажется лишним, пока не понадобится закоммитить только часть накопленных правок, когда исправление формулы уходит одним коммитом, а эксперименты с графиками — другим. Ради этого он и заведён.

### Коммиты образуют граф

Каждый коммит ссылается на родителя, поэтому история образует направленный ациклический граф (DAG). Пока работаешь один, он вырождается в цепочку; ветки заставляют его ветвиться, а слияния снова сходиться.

```text
A ─── B ─── C ─────── F      main
       └── D ─── E ───┘      fft-filter
```

**Ветка** в Git представляет собой подвижный указатель на коммит, буквально файл на 41 байт, лежащий внутри `.git`, и никакой копии проекта не создаётся, поэтому ветки заводятся мгновенно и бесплатно. **HEAD** указывает на то место в графе, где ты сейчас находишься.

## Базовый цикл работы

### Разовая настройка

```bash
# представься: имя и почта попадут в каждый твой коммит
git config --global user.name "Lev Landau"
git config --global user.email "l.landau@g.nsu.ru"

# называть главную ветку main, как принято на GitHub
git config --global init.defaultBranch main
```

### Создать или склонировать репозиторий

```bash
# превратить текущую папку в репозиторий (появится скрытая папка .git)
git init

# или склонировать существующий проект с сервера
git clone https://github.com/nsu-phys/beam-dynamics.git
```

### Правки → индекс → коммит

В основной петле, описанной ниже, проходит почти вся повседневная работа.

```bash
git status                  # что изменилось? (спрашивай постоянно)

git add processing.py       # добавить файл в индекс
git add plots/              # можно папку целиком
git add -p                  # интерактивно, по кускам — очень полезно

git commit -m "Учтена поправка на температуру датчика"

git status                  # убедиться, что всё зафиксировано
```

`git status` остаётся самой недооценённой командой, показывающей состояние всех трёх зон и заодно подсказывающей следующий шаг. Первое время вызывай её до и после каждой операции.

### Смотрим историю и различия

```bash
git log                     # полная история с авторами и датами
git log --oneline           # по строчке на коммит
git log --oneline --graph --all   # весь граф с ветками, псевдографикой

git diff                    # что поменялось, но ещё не добавлено в индекс
git diff --staged           # что уже в индексе и войдёт в коммит
git diff a3f2c17 HEAD -- processing.py  # как файл изменился со старого коммита

git show a3f2c17            # что именно сделал этот коммит
```

## .gitignore: что не должно попасть в репозиторий

Git отслеживает только явно добавленные тобой файлы, но `git status` будет назойливо перечислять всё подряд, от кешей Python до гигабайтных файлов, набитых данными. Файл `.gitignore`, лежащий в корне проекта, говорит, что игнорировать. Вот заготовка, собранная для типичного научного проекта.

```gitignore
# байткод и кеши Python
__pycache__/
*.pyc
.ipynb_checkpoints/

# виртуальное окружение
.venv/

# данные измерений и результаты расчётов — им не место в git
data/
*.h5
*.root
*.npz

# тяжёлые артефакты: чекпойнты моделей, дампы
checkpoints/
*.ckpt

# мусор редакторов и ОС
.idea/
.vscode/
.DS_Store

# LaTeX-мусор
*.aux
*.synctex.gz
```

Правило простое. В репозитории живёт написанное руками (код, тексты, конфиги), и не живёт измеренное на установке или сгенерированное расчётом. Сам `.gitignore` коммитится в репозиторий, поскольку правила исключений, принятые в проекте, общие для всей группы.

## Ветки

Ветка даёт возможность экспериментировать, не трогая работающий код, так что если хочешь попробовать другой алгоритм фильтрации сигнала, не комментируй полфайла, а заведи ветку, названную по сути эксперимента.

```bash
git branch                    # список веток, звёздочка — текущая
git switch -c fft-filter      # создать ветку и переключиться на неё
# ...правишь и коммитишь сколько угодно...
git switch main               # вернуться на main: файлы мгновенно
                              # станут такими, какими были там
```

`git switch` появился в Git 2.23; в старых руководствах то же самое делают `git checkout -b fft-filter` и `git checkout main`, и эти команды взаимозаменяемы.

### Слияние

Когда эксперимент, поставленный в ветке, удался, влей её обратно:

```bash
git switch main
git merge fft-filter          # влить коммиты fft-filter в main
git branch -d fft-filter      # удалить ненужный больше указатель
```

Если `main` с момента ветвления не менялся, Git просто передвинет указатель вперёд (fast-forward). Если менялся, появится коммит слияния, связанный сразу с двумя родителями, и граф из картинки выше снова сходится в одну линию.

### Конфликты

Если в двух ветках изменены одни и те же строки, Git честно откажется выбирать за тебя и вставит в файл маркеры, размечающие обе версии:

```text
<<<<<<< HEAD
dt = 1e-12  # шаг интегрирования для жёсткой задачи
=======
dt = 5e-12  # компромисс между точностью и скоростью
>>>>>>> fft-filter
```

Конфликт — не поломка, а вполне разрешимый вопрос, заданный тебе системой. Отредактируй файл, оставив правильный вариант или скомбинировав оба, удали расставленные маркеры и заверши слияние:

```bash
git add integrator.py         # пометить конфликт разрешённым
git commit                    # завершить merge
```

Если же ты решил не сливать вовсе, то вместо двух перечисленных команд нужна одна:

```bash
git merge --abort             # откатить слияние целиком
```

Порядок здесь важен. После `git commit` сливать уже нечего, и `git merge --abort` ответит, что отменять нечего.

Чем мельче коммиты и чем чаще ты сливаешь ветки, тем реже и безобиднее конфликты, достающиеся тебе на разбор.

## Удалённые репозитории

Пока коммиты лежат только на твоём ноутбуке, нет ни резервной копии, ни совместной работы, поэтому нужен удалённый репозиторий (remote), хранящий копию проекта на GitHub, GitLab или на институтской машине, выделенной группе.

```bash
git remote -v                  # список удалённых репозиториев
# после git clone там уже есть origin — адрес, откуда клонировал

# привязать локальный репозиторий к созданному на GitHub
git remote add origin git@github.com:username/beam-dynamics.git

git push -u origin main        # отправить ветку main на сервер;
                               # -u запоминает связку, дальше просто git push

git fetch                      # скачать чужие коммиты, НЕ трогая твои файлы
git pull                       # fetch + merge: скачать и влить в текущую ветку
git push                       # отправить свои коммиты
```

`git fetch` безопасен всегда, поскольку лишь обновляет локальное знание о сервере, после чего можно спокойно посмотреть `git log origin/main` и разобрать коммиты, принесённые коллегами. `git pull` объединяет `fetch` с немедленным слиянием. Типовой ритм работы, принятый в любой группе, прост: сел за работу, сделай `git pull`, закончил, сделай `git push`. Чем чаще синхронизируешься, тем меньше конфликтов.

### Fork + pull request

В чужой репозиторий, будь то библиотека вроде `numpy` или проект соседней лаборатории, напрямую пушить нельзя. Стандартный механизм совместной работы, отлаженный за годы, выглядит так:

1.  **Fork**. Кнопкой на GitHub делаешь личную копию репозитория, привязанную к твоему аккаунту.
2.  Клонируешь свой форк, создаёшь ветку, коммитишь исправление.
3.  Пушишь ветку в свой форк.
4.  Открываешь **pull request (PR)**, то есть предложение «заберите мои коммиты к себе», снабжённое описанием и дифом.
5.  Владельцы читают код, пишут замечания (code review), ты дополняешь ветку новыми коммитами, и PR обновляется автоматически.
6.  Когда всех всё устраивает, PR, одобренный владельцами, вливают в основной репозиторий.

Так живёт весь open source и заметная часть открытой науки. Исправление даже одной строки в документации `scipy` проходит тот же путь. Внутри своей группы обычно пушат в общий репозиторий, но правки всё равно оформляют ветками и PR ради ревью.

## Хорошие практики

Держи коммиты атомарными, по одному логическому изменению на коммит. «Исправлена нормировка спектра» и «добавлен скрипт карты магнитного поля» дают два коммита, а не один «изменил всякое». Атомарный коммит, несущий одну мысль, можно понять, откатить или перенести целиком, а коммит-свалку нельзя. По той же причине старайся, чтобы проект в каждом коммите хотя бы запускался, и тогда любая точка истории, выбранная наугад, годится для поиска момента, где всё сломалось.

Столько же значит и сообщение. Слово `fix` не отвечает ни на один вопрос о том, что починили, где и почему. Через полгода `git log`, состоящий из `fix`, `fix2` и `wip`, превращается в археологические раскопки, съедающие целый вечер. Диф и так покажет, *что* поменялось. Пиши короткий заголовок, передающий суть изменения, не «поменял коэффициент», а «Увеличен шаг сетки: старый не влезал в память на кластере». По соглашению, принятому повсеместно, заголовок укладывают в 50 символов и уж точно не растягивают дальше 72. Сообщение, читаемое через год, должно объяснять, *зачем*.

Отдельный разговор идёт о том, чего в репозитории быть не должно. Git, созданный для текста, плохо переносит большие бинарники. Каждый попавший в историю гигабайт останется в ней навсегда, и клонирование станет невыносимым. Сырые данные с установки, HDF5/ROOT-файлы, видео, обученные модели в репозиторий не кладут. Для версионирования больших файлов рядом с кодом существуют [Git LFS](https://git-lfs.com/) (в git хранятся лишь ссылки, а содержимое лежит на отдельном сервере) и [DVC](https://dvc.org/) (Data Version Control, версионирующий данные и пайплайны обработки, а сами файлы складывающий в любое хранилище, хоть в облако, хоть на сетевой диск группы). И никогда не коммить пароли, токены и ключи, потому что вычистить секрет, попавший в историю, почти невозможно, а сделанные коллегами клоны успевают разойтись.

## Если что-то пошло не так

Главное успокоительное состоит в том, что закоммиченное почти невозможно потерять: Git скорее сохранит лишнее, чем удалит нужное. Ниже собрана шпаргалка, покрывающая типовые ситуации.

| Ситуация | Команда |
|----------|---------|
| Испортил файл, хочу версию из последнего коммита | `git restore file.py` (незакоммиченные правки исчезнут!) |
| Сделал `git add` лишнего | `git restore --staged file.py` (убирает из индекса, правки останутся) |
| Опечатка в сообщении последнего коммита или забыл файл | `git commit --amend` (только пока не запушил) |
| Хочу «рассыпать» последний коммит обратно в правки | `git reset --soft HEAD~1` (коммит исчез, изменения остались в индексе) |
| Выкинуть последний коммит **вместе с изменениями** | `git reset --hard HEAD~1` (**опасно**, правки будут уничтожены) |
| Отменить уже запушенный коммит | `git revert a3f2c17` (новый коммит с обратным изменением, история не переписывается) |
| Срочно нужна другая ветка, а правки не закончены | `git stash` прячет изменения, `git stash pop` возвращает |
| «Я всё сломал, коммиты пропали» | `git reflog`, журнал последних положений HEAD; найди нужный хеш и вернись командой `git reset --hard <хеш>` |

Про `git reset --hard` запомни отдельно, ведь это одна из немногих команд, молча и непоправимо уничтожающих незакоммиченную работу. Прежде чем её набирать, сделай `git status` и убедись, что терять нечего. Историю переписывает и `git rebase`, переносящий коммиты ветки поверх другой так, будто они там и делались: граф выходит линейным и читаемым, но у перенесённых коммитов новые хеши, то есть прежних коммитов больше нет. И не переписывай историю (`reset`, `--amend`, `rebase`) в ветках, уже запушенных на сервер и подхваченных коллегами. Иначе коллегам придётся разгребать разъехавшийся граф.
