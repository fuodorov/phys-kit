# Docker

Пространства имён и контрольные группы мы только что разобрали изнутри; теперь посмотрим, во что их упаковали. Код, оторванный от окружения, ничего не воспроизводит, поскольку расчёт зависит ещё и от версии Python, набора библиотек, системных пакетов и десятка настроек, отсутствующих в репозитории. На этом стыке и ломается воспроизводимость чужих результатов, а закрывает его инструмент, разобранный ниже.

## «У меня на машине работает»

Ситуация знакома каждому. Ты написал скрипт обработки данных, полученных на эксперименте, он прекрасно работает на твоём ноутбуке, а отправляешь коллеге, и у него всё падает с `ImportError`. Запускаешь на кластере, где стоит Python 3.8 вместо твоего 3.12, системный `numpy` собран без нужных флагов, а права на установку пакетов есть только у администратора, уехавшего в отпуск. Через два года рецензент просит воспроизвести график, напечатанный в статье, а ты уже и сам не помнишь версий библиотек, стоявших тогда.

Для физики это не мелкая бытовая неприятность, а удар по главному принципу науки, по воспроизводимости. Численный результат, не поддающийся повторению, стоит немногим больше, чем результат, которого нет. Виртуальные окружения и `requirements.txt` решают проблему лишь частично, так как фиксируют версии установленных Python-пакетов, но не версию самого Python, не системные библиотеки (BLAS, LAPACK, HDF5, компиляторы), не переменные окружения и не операционную систему. Как их заводят и чем наполняют, разбирается дальше, в главе [«От скрипта к приложению»](./app.md); здесь достаточно знать, что это способ зафиксировать список Python-пакетов проекта.

Docker решает проблему радикально, поскольку ты упаковываешь приложение **вместе со всем его окружением**, с интерпретатором, библиотеками, системными зависимостями и настройками, в единый образ. Собранный образ запускается одинаково на твоём ноутбуке, на машине коллеги и на сервере, стоящем в лаборатории. «У меня работает» превращается в «работает у всех».

## Контейнеры vs виртуальные машины

Первым делом хочется сказать «это же виртуальная машина». Нет, и разница, отделяющая одно от другого, принципиальна. Виртуальная машина эмулирует целый компьютер, несущий внутри полноценную гостевую операционную систему со своим ядром, а гипервизор транслирует её обращения к железу. Изоляция, купленная такой ценой, получается надёжной, но дорогой, потому что каждая ВМ занимает гигабайты и стартует десятки секунд.

Контейнер же представляет собой обычный процесс операционной системы, которому ядро Linux «подкрутило» два названных ниже механизма. **Namespaces** (пространства имён) изолируют то, что процесс *видит*, и у контейнера свои дерево процессов, сетевые интерфейсы и файловая система, а сам он искренне считает себя единственным в системе. **Cgroups** (control groups) ограничивают то, что процесс *потребляет*, то есть отпущенные ему память, процессорное время и дисковый ввод-вывод. Ядро при этом остаётся общим для всех контейнеров и хоста, поэтому контейнер стартует за доли секунды, а образ весит от десятков до сотен мегабайт вместо гигабайт, занимаемых виртуальной машиной. Платой за лёгкость служит изоляция, чуть более слабая, чем у ВМ, что важно для запуска чужого недоверенного кода и несущественно для упаковки собственных расчётов. Пространства имён и контрольные группы разобраны в предыдущей главе, так что здесь достаточно помнить: контейнер — это процесс, а не машина.

На macOS и Windows нативных Linux-контейнеров не бывает, поэтому Docker Desktop незаметно для тебя держит лёгкую виртуальную машину с Linux, спрятанную от глаз, внутри которой и живут контейнеры.

## Образы и контейнеры

Два центральных понятия, которые важно не путать:

- **Образ (image)** представляет собой неизменяемый шаблон, то есть файловую систему с поставленными в неё программами плюс метаданные (какую команду запускать, какие порты открывать). В терминах программирования образ соответствует классу.
- **Контейнер (container)** служит запущенным экземпляром образа, живым процессом со своим состоянием, объектом названного класса. Из одного образа можно запустить хоть сотню контейнеров.

Начнём с готовых образов, которые скачивают из реестра, по умолчанию из Docker Hub.

```bash
# скачать официальный образ Python 3.12 (slim — урезанный, без лишнего)
docker pull python:3.12-slim

# список локально скачанных образов
docker images
```

Запись `python:3.12-slim` читается как «репозиторий:тег», где тег означает версию. Если тег не указать, подставится `latest`, но в науке так поступать не принято. Образ, помеченный `latest` сегодня и через год, окажется разным, а нам нужна воспроизводимость.

Теперь запустим контейнер:

```bash
# запустить контейнер и выполнить в нём одну команду
docker run python:3.12-slim python -c "print('hello from container')"

# интерактивный запуск: -i — пробросить stdin, -t — выделить терминал
# получаем REPL питона внутри контейнера
docker run -it python:3.12-slim python

# а так можно попасть в шелл контейнера и осмотреться
docker run -it python:3.12-slim bash

# --rm — удалить контейнер сразу после завершения (не копить мусор)
docker run --rm -it python:3.12-slim bash
```

Внутри контейнера ты оказываешься в изолированном мире, где команда `ls /` покажет чужую файловую систему, `pip install` поставит пакет *внутри контейнера*, и после его удаления всё исчезнет. Это фича, а не баг. Контейнеры эфемерны, всё ценное должно жить либо в образе, либо в примонтированных томах (о них ниже).

Управление контейнерами:

```bash
docker ps               # запущенные контейнеры
docker ps -a            # все, включая остановленные
docker stop <id|имя>    # мягко остановить контейнер
docker rm <id|имя>      # удалить остановленный контейнер
docker rmi <образ>      # удалить образ
docker logs <id|имя>    # посмотреть, что контейнер писал в stdout/stderr
```

Вместо полного идентификатора можно писать первые несколько символов или имя, выданное контейнеру самим Docker (или задать своё через `--name`).

### Проброс портов и томов

Контейнер изолирован, в том числе по сети и по файлам, поэтому, чтобы он приносил пользу, изоляцию прокалывают в нужных местах двумя флагами.

**Порты, `-p хост:контейнер`.** Сервис, запущенный внутри контейнера, слушает отведённый ему порт, и снаружи его не видно, пока ты не пробросишь порт на хост.

**Тома, `-v путь_на_хосте:путь_в_контейнере`.** Каталог хоста монтируется внутрь контейнера, файлы видны с обеих сторон, а полученные результаты переживают удаление контейнера.

Классический пример для физика даёт Jupyter, поднятый в контейнере без единого `pip install` на своей машине.

```bash
# jupyter/scipy-notebook — готовый образ с numpy, scipy, pandas, matplotlib
# -p 8888:8888          порт 8888 хоста -> порт 8888 контейнера
# -v ...:/home/jovyan/work   текущий каталог -> каталог work внутри контейнера
# тег фиксируем ради воспроизводимости, реестр указываем явно:
# образы jupyter в конце 2023 года переехали с Docker Hub на quay.io
docker run --rm \
    -p 8888:8888 \
    -v "$(pwd)":/home/jovyan/work \
    quay.io/jupyter/scipy-notebook:2024-05-27
```

Открываешь в браузере `http://localhost:8888` по ссылке с токеном, выведенной контейнером в лог, и работаешь в блокнотах, физически лежащих в твоём текущем каталоге. Удалишь контейнер, и блокноты останутся, а окружение исчезнет без следа.

## Dockerfile: свой образ для научного проекта

Чужие образы хороши, но твой расчётный код требует своего набора зависимостей, а рецепт сборки образа описан в файле `Dockerfile`. Пусть у нас есть проект, посвящённый моделированию динамики пучка.

```
beam-simulation/
├── Dockerfile
├── requirements.txt      # numpy, scipy, matplotlib с версиями
├── simulate.py           # основной расчёт
└── beamlib/              # свои модули
```

Содержимое `requirements.txt`:

```
numpy==2.1.3
scipy==1.14.1
matplotlib==3.9.2
```

А вот `Dockerfile`:

```dockerfile
# Базовый образ: официальный Python, slim-вариант без лишних пакетов.
# Всегда фиксируй версию — это фундамент воспроизводимости.
FROM python:3.12-slim

# Рабочий каталог внутри образа; все следующие команды выполняются в нём.
# Если каталога нет, он будет создан.
WORKDIR /app

# Сначала копируем ТОЛЬКО файл с зависимостями...
COPY requirements.txt .

# ...и устанавливаем их. --no-cache-dir не хранит кеш pip в образе,
# образ получается меньше.
RUN pip install --no-cache-dir -r requirements.txt

# Только теперь копируем весь остальной код проекта.
COPY . .

# Команда по умолчанию при запуске контейнера.
# Форма со скобками (exec form) запускает процесс напрямую, без оболочки.
CMD ["python", "simulate.py"]
```

Разберём инструкции:

- `FROM` называет образ, наследуемый нами. Всё, что есть в `python:3.12-slim` (Debian, Python, pip), достаётся нам бесплатно.
- `WORKDIR /app` объявляет текущий каталог для последующих `COPY`, `RUN`, `CMD`.
- `COPY <откуда> <куда>` копирует файлы из каталога проекта, называемого контекстом сборки, внутрь образа.
- `RUN` выполняет команду **во время сборки** и запекает полученный результат в образ. Сюда же ставят системные пакеты вроде `RUN apt-get update && apt-get install -y gfortran`.
- `CMD` указывает, что запускать **при старте контейнера**. Выполняется не при сборке, а при `docker run`, и легко переопределяется командой `docker run мой-образ bash`.

### Слои и кеширование: почему requirements.txt копируют отдельно

Каждая инструкция Dockerfile создаёт **слой** — снимок изменений, внесённых ею в файловую систему. Образ представляет собой стопку слоёв, кешируемых Docker: если инструкция и её входные файлы не изменились, слой берётся из кеша, а не пересобирается. Но как только один слой изменился, все последующие пересобираются заново.

Теперь смотри на порядок, выбранный в нашем Dockerfile. Код (`simulate.py`) ты правишь по двадцать раз на дню, а `requirements.txt` раз в месяц. Если бы мы писали `COPY . .` до установки зависимостей, любая правка, сделанная в коде, инвалидировала бы слой копирования, и Docker заново гонял бы `pip install` со скачиванием numpy и scipy. Пять минут ожидания после каждой изменённой строчки. А в нашем порядке слой с зависимостями зависит только от `requirements.txt`, так что правишь код, и пересобирается лишь копеечный `COPY . .`, сборка занимает секунды. Правило простое: **редко меняющееся выше, часто меняющееся ниже**.

Ещё одну полезную деталь даёт файл `.dockerignore`, устроенный по образцу `.gitignore`. Перечисли в нём `.git`, `__pycache__`, данные и прочее, что не должно попадать в образ.

## Сборка и запуск

```bash
# Собрать образ из Dockerfile в текущем каталоге (точка — контекст сборки).
# -t задаёт имя и тег.
docker build -t beam-simulation:0.1 .

# Тег можно навесить и потом (это просто ярлык на тот же образ)
docker tag beam-simulation:0.1 beam-simulation:latest

# Запуск: результаты пишем в примонтированный каталог,
# иначе они умрут вместе с контейнером
docker run --rm -v "$(pwd)/results":/app/results beam-simulation:0.1

# Переопределить CMD: запустить другой скрипт из того же образа
docker run --rm beam-simulation:0.1 python -m beamlib.diagnostics
```

Теперь весь расчёт сводится к одной команде, воспроизводимой на любой машине с Docker.

## Реестры: Docker Hub и ghcr.io

Образ собран, осталось передать его коллеге. Можно выгрузить в файл (`docker save` и `docker load`), но путь, ставший стандартным, лежит через **реестр** (registry), устроенный как git-хостинг для образов. По умолчанию используется публичный [Docker Hub](https://hub.docker.com/), оттуда мы качали `python:3.12-slim`. Второй популярный вариант, GitHub Container Registry (`ghcr.io`), удобен тем, что образы живут рядом с кодом проекта на GitHub и собираются автоматически через GitHub Actions.

Публикация выглядит просто. Имя образа, отправляемого в реестр, должно включать твой аккаунт, а дальше идёт `docker push`.

```bash
# тегируем образ под свой аккаунт на Docker Hub
docker tag beam-simulation:0.1 fuodorov/beam-simulation:0.1

docker login                            # авторизация (однократно)
docker push fuodorov/beam-simulation:0.1

# коллега на любой машине делает:
docker pull fuodorov/beam-simulation:0.1

# для ghcr.io всё то же, только префикс реестра в имени:
docker tag beam-simulation:0.1 ghcr.io/fuodorov/beam-simulation:0.1
docker push ghcr.io/fuodorov/beam-simulation:0.1
```

## Docker Compose: когда контейнеров больше одного

Реальная система редко состоит из одного контейнера, и типичным оказывается сценарий с приложением, пишущим снятые результаты в базу данных PostgreSQL. Запускать оба контейнера руками, настраивать связывающую их сеть, помнить порядок запуска и десяток флагов тоскливо. Docker Compose описывает всю связку декларативно, в одном файле `compose.yaml`:

```yaml
services:
  app:
    build: .                    # собрать образ из Dockerfile в текущем каталоге
    volumes:
      - ./results:/app/results  # результаты — на хост
    environment:
      DB_HOST: db               # имя сервиса работает как сетевое имя хоста
      DB_USER: physicist
      DB_PASSWORD: secret
    depends_on:
      - db                      # сначала стартует база, потом приложение

  db:
    image: postgres:16          # готовый образ с Docker Hub
    environment:
      POSTGRES_USER: physicist
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: measurements
    volumes:
      - pgdata:/var/lib/postgresql/data   # именованный том: данные переживут контейнер

volumes:
  pgdata:
```

Compose автоматически создаёт общую сеть, в которой контейнеры видят друг друга по именам сервисов, объявленным в файле, и приложение подключается к базе просто по адресу `db:5432`, безо всяких IP. Управление сводится к двум командам:

```bash
docker compose build      # только собрать образы, не запуская
docker compose up -d      # собрать и запустить всё; -d — в фоне
docker compose logs -f    # смотреть логи всех сервисов
docker compose ps         # какие сервисы подняты и какие порты опубликованы
docker compose down       # остановить и удалить контейнеры (тома останутся)
```

Одного файла, закоммиченного в репозиторий, хватает, чтобы любой член группы поднял всю инфраструктуру, описанную в проекте, одной командой.

### Что видно снаружи, а что только внутри

В примере выше наружу не торчит ничего: и приложение, и база разговаривают
только между собой, по сети, поднятой самим Compose. Как только сервис нужно
открыть человеку или соседней машине, в дело идут два разных ключа, и путать
их не стоит.

```yaml
services:
  nginx:
    image: nginx:1.27
    ports:
      - "80:80"     # опубликовать наружу: порт 80 хоста -> порт 80 контейнера
  backend:
    build: ./backend
    expose:
      - "8000"      # видно только соседям по сети Compose, с хоста не достучаться
```

`ports` пробивает порт на хост, и по нему в контейнер придёт кто угодно, у кого
есть доступ к машине. `expose` не публикует ничего, а лишь помечает порт, на
котором сервис слушает, для соседей по той же сети. Отсюда обычная раскладка
боевого стенда: снаружи опубликован единственный порт, а за ним стоит nginx,
раздающий статику фронтенда и переправляющий запросы к API на бэкенд по
имени сервиса. Такой nginx называют обратным прокси, и в его конфиге
достаточно одной секции:

```nginx
server {
    listen 80;
    location / {
        root /usr/share/nginx/html;     # собранный фронтенд
    }
    location /api/ {
        proxy_pass http://backend:8000/;   # backend — имя сервиса из compose.yaml
    }
}
```

Выигрыш здесь не только в аккуратности. Порт, не опубликованный наружу,
нельзя атаковать с хоста и из сети, а значит, база данных и бэкенд остаются
недосягаемыми, даже если в них найдётся дыра. Проверяется всё это командой
`docker compose ps`: публикация должна стоять ровно у одного сервиса, а `curl`
на порт бэкенда с хоста отвечать не должен.

## Контейнеры в науке

Контейнер служит готовым ответом рецензенту, требующему воспроизвести твои результаты. Всё чаще к статье прикладывают не только код, но и собранный образ или хотя бы Dockerfile, положенный в репозиторий. Одна команда `docker run`, и читатель получает те же графики из тех же данных, с точностью до версий всех задействованных библиотек. Есть нюанс с кластерами: на суперкомпьютерах Docker обычно запрещён из-за демона, работающего с правами root. Там используют [Apptainer](https://apptainer.org/) (бывший Singularity), контейнерную систему, спроектированную для HPC, которая работает без root-прав, дружит с MPI и GPU и умеет напрямую конвертировать Docker-образы. Поэтому образ, собранный для ноутбука, почти без изменений поедет и на кластер.
