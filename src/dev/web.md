# Основы компьютерных сетей и веб-технологий

Разбираться в сетях физику приходится потому, что почти любые данные, нужные для работы, сегодня добываются через сеть. Установка отдаёт телеметрию по TCP, каталог наблюдений живёт за HTTP-интерфейсом, расчёт запускается на кластере по SSH, а результаты уезжают на сервер группы. И когда что-то из этого перестаёт работать, вопрос о месте разрыва решается быстро только у того, кто представляет дорогу, проложенную от программы до провода.

Эта глава написана обзорно. Сетевым инженером она тебя не сделает, зато даст карту местности: какие уровни существуют, за что отвечает каждый, какими инструментами смотреть на каждом из них и как обращаться к сети из Python.

## Сетевые модели: OSI и TCP/IP

Сеть устроена слоями. Это главная идея, без которой дальше не разобраться. Каждый слой решает свою узкую задачу и пользуется услугами слоя, лежащего ниже, ничего не зная о его внутреннем устройстве. Приложение говорит «отправь эти байты на такой-то адрес» и не думает ни о маршрутах, ни о том, медный там кабель или оптика.

Разделение, проведённое так, — не академическая красивость, а инженерная необходимость. Благодаря ему Wi-Fi изобрели, не переписывая ни браузеры, ни протокол IP.

Классическая **модель OSI**, придуманная как эталонная, насчитывает семь уровней:

| № | Уровень | Чем занимается | Единица данных |
|---|---|---|---|
| 7 | Прикладной | протоколы приложений HTTP, DNS, FTP | данные |
| 6 | Представления | кодировки, сжатие, шифрование | данные |
| 5 | Сеансовый | управление сессиями связи | данные |
| 4 | Транспортный | доставка между процессами, TCP и UDP | сегмент |
| 3 | Сетевой | маршрутизация между сетями по IP | пакет |
| 2 | Канальный | передача между соседними узлами | кадр |
| 1 | Физический | биты через провод или эфир | бит |

На практике же пользуются более скупой **моделью TCP/IP** из четырёх уровней. Физический и канальный в ней объединены в «уровень сетевого доступа», а три верхних уровня OSI слиты в один прикладной. Так интернет и устроен; дальше мы пойдём по этой модели снизу вверх.

## Уровень сетевого доступа

Самый нижний уровень отвечает на вопрос «как физически доставить биты соседу».

### Физический уровень

Здесь живёт материя — витая пара и коаксиальный кабель, оптоволокно (одномодовое для дальних линий, многомодовое для коротких), радио в виде Wi-Fi по стандарту 802.11, Bluetooth и сотовой связи. Уровень решает единственную задачу, превращая единицы и нули в сигнал и обратно.

Среду передачи описывают скоростью, полосой пропускания, затуханием сигнала и помехоустойчивостью. А проблемы, случающиеся на этом уровне, самые прозаические: перебитый кабель, наводка от силового шкафа, криво обжатый коннектор, растянутый сверх нормы сегмент. В лаборатории они и дают большую часть загадочных жалоб «сеть тормозит», поэтому диагностику начинают снизу, с проверки того, горит ли вообще линк.

### Канальный уровень

Уровнем выше принятые биты собираются в **кадры** (frames) и передаются между устройствами, которые находятся внутри одной локальной сети. Основными технологиями, применяемыми здесь, служат Ethernet (стандарт IEEE 802.3) и Wi-Fi (IEEE 802.11), а для соединений «точка-точка» PPP.

Адресация, принятая на этом уровне, своя. У каждого сетевого интерфейса есть **MAC-адрес** — идентификатор, зашитый производителем. Отсюда возникает задача, решаемая протоколом **ARP**. Программа знает IP-адрес получателя, а отправить кадр нужно на MAC-адрес, и ARP выясняет соответствие, связывающее их, опрашивая локальную сеть. Ещё одна вещь, встречающаяся в институтских сетях, называется **VLAN** и означает логическое разделение одной физической сети на независимые сегменты, которые не видят друг друга, чтобы, скажем, сеть управления установкой не пересекалась с офисной.

Посмотреть на кадры, бегающие на этом уровне, можно так.

```bash
ip link show          # список сетевых интерфейсов и их состояние
ethtool eth0          # скорость, режим дуплекса, статистика ошибок
arp -a                # таблица соответствия IP-адресов и MAC-адресов
```

## Сетевой уровень

Канальный уровень умеет доставлять собранные кадры только внутри одной локальной сети. Чтобы дотянуться до машины, стоящей в другом городе, нужен уровень выше, **сетевой**, с главным протоколом IP.

IP решает две задачи: даёт каждому узлу адрес, понятный глобально, и прокладывает путь между сетями.

### Адресация

**IPv4** задаёт 32-битный адрес, записываемый четырьмя октетами, как `192.168.1.1`. Всего таких адресов около четырёх миллиардов, и они давно кончились, отсюда весь зоопарк с трансляцией адресов, видимый в любой домашней или институтской сети.

Часть диапазонов зарезервирована под **частные сети**: их адреса не маршрутизируются в интернет и могут повторяться в разных организациях:

* `10.0.0.0/8` для больших корпоративных сетей;
* `172.16.0.0/12` для сетей средних размеров;
* `192.168.0.0/16`, тот самый диапазон, розданный домашним роутерам.

Запись вида `/24` после адреса называется префиксом и говорит, сколько старших битов адреса отведено под номер сети. Запись `192.168.1.0/24` описывает сеть из 256 адресов, различающихся только последним октетом.

**IPv6** решает проблему, накопившуюся с адресами, радикально. Адрес занимает 128 бит и записывается восемью группами по четыре шестнадцатеричные цифры, как `2001:0db8:85a3:0000:0000:8a2e:0370:7334`. Длинные цепочки нулей разрешено сокращать двойным двоеточием, и записанный выше адрес превращается в `2001:db8:85a3::8a2e:370:7334`.

### Маршрутизация

Маршрутизация отвечает на вопрос «куда отправить принятый пакет дальше». Каждый узел, включая твой ноутбук, хранит таблицу маршрутов и для каждого пакета выбирает подходящую строку из записанных в ней. Таблицу, заполненную на твоей машине, можно посмотреть так.

```bash
$ ip route show
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100
10.0.0.0/8 via 192.168.1.254 dev eth0
```

Выбирается всегда самая конкретная из подходящих строк. Пакет в сеть `192.168.1.0/24` уходит прямо в интерфейс `eth0`, пакет в `10.0.0.0/8` идёт через шлюз `192.168.1.254`, а всё, не подошедшее ни под одну строку, попадает в `default`. Когда сервер соседнего корпуса не отвечает, а до машины, стоящей в своей комнате, `ping` проходит, смотреть надо сюда, потому что чаще всего до нужной сети просто нет проложенного маршрута.

Таблица, впрочем, не одна. Какую из имеющихся смотреть для конкретного пакета, решают правила маршрутизации. Они пригодятся машине, подключённой сразу к двум сетям, скажем к институтской и к сети управления установкой:

```bash
$ ip rule
0:    from all lookup local
32766: from all lookup main
32767: from all lookup default
```

Когда маршрут проложен, а пакеты всё равно не доходят, остаётся выяснить, где они теряются. Команда `ip route get` показывает маршрут, выбираемый ядром для конкретного адреса; `traceroute` перечисляет узлы, через которые пакет проходит по пути; `mtr` крутит то же самое непрерывно и сразу считает потери, набегающие на каждом переходе, давая самый быстрый способ показать сетевикам, на каком узле рвётся:

```bash
traceroute 8.8.8.8
mtr 8.8.8.8
ip route get 8.8.8.8
```

## Транспортный уровень

IP доставляет пакет до машины, но на ней работают десятки программ. Кому из них предназначен пришедший пакет, говорит номер **порта**, и это первая забота транспортного уровня. Вторая забота состоит в надёжности доставки, и тут выбирают из двух протоколов, руководствуясь тем, что дороже, потеря данных или задержка.

### UDP: быстро и без гарантий

UDP не устанавливает соединения, не подтверждает доставку, не следит за порядком приходящих пакетов и не борется с перегрузками. Отправил и забыл. Отправленный пакет может потеряться, прийти дважды или обогнать предыдущий, и протокол об этом даже не узнает.

Звучит как недостаток, но за отсутствие всех перечисленных механизмов UDP получает минимальные накладные расходы и задержку. Поэтому на нём работают DNS-запросы (проще переспросить, чем поддерживать соединение), голосовая связь, онлайн-игры и видеотрансляции. Там потерянный кусок уже не нужен: пока его переспрашивают, разговор, идущий дальше, уйдёт вперёд.

### TCP: надёжно, но дороже

TCP гарантирует, что данные дойдут целиком, в правильном порядке и без дубликатов. Достигается это ценой установленного соединения, подтверждений, повторных передач и контроля перегрузок.

Соединение открывается **тройным рукопожатием**, описанным ниже:

1. клиент шлёт серверу `SYN`, означающий «хочу соединиться»;
2. сервер отвечает `SYN-ACK`, означающим «согласен, и я тоже хочу»;
3. клиент отвечает `ACK`, то есть «принято». Соединение, установленное так, готово к передаче.

Три пакета, отправленных до первого байта полезных данных, и составляют ту задержку, которой избегает UDP.

Все обещания, данные TCP, держатся на полях его заголовка.

```text
| Порт отправителя      | Порт получателя       |
| Номер последовательности (Sequence Number)    |
| Номер подтверждения (Acknowledgment Number)   |
| Смещение | Резерв | Флаги | Размер окна      |
| Контрольная сумма     | Указатель срочности   |
```

Номер последовательности позволяет собрать пришедшие байты в правильном порядке, номер подтверждения сообщает, что дошло, а размер окна говорит отправителю, сколько данных можно слать, не дожидаясь подтверждений.

### Контроль перегрузок

Отдельного упоминания заслуживает механизм, остающийся незамеченным, пока не начнутся странности с измеренной скоростью. TCP не знает пропускной способности проложенного пути заранее и вынужден нащупывать её, разгоняясь, пока не начнутся потери, и сбрасывая скорость, когда они появились. Алгоритмов, нащупывающих её, придумано много:

* **Tahoe и Reno**, классика, реагирующая на потерянный пакет резким снижением скорости;
* **CUBIC**, поставленный в Linux по умолчанию, восстанавливает потерянную скорость агрессивнее;
* **BBR**, современный подход от Google, вместо потерь ориентируется на измеренную полосу и задержку, что заметно лучше работает на длинных линиях, тянущихся между городами.

Отсюда вывод, полезный на практике. Если файл копируется между корпусами института медленнее, чем позволяет проложенный канал, дело нередко не в «плохой сети», а в том, как алгоритм контроля перегрузок реагирует на редкие потери, возникающие при большой задержке.

Посмотреть на состояние открытых соединений можно так.

```bash
ss -tn                      # открытые TCP-соединения
ss -tlnp                    # какие порты слушают и какие процессы
tcpdump -i any tcp port 80  # перехват пакетов на порту 80
```

## Прикладной уровень

Мы добрались до уровня, населённого самими программами. Здесь живут протоколы, знакомые тебе напрямую: DNS переводит имена в адреса, HTTP переносит упакованные данные, TLS их шифрует.

### DNS: из имён в адреса

Компьютеры адресуют друг друга числами, а люди запомненными именами. Мостом, переброшенным между ними, служит **система доменных имён** — распределённая база, из которой по имени `example.com` возвращается его IP-адрес.

Хранятся в ней записи разных типов. Чаще всего встречаются четыре, перечисленные ниже:

| Тип | Что содержит |
|---|---|
| `A` / `AAAA` | адрес IPv4 / IPv6 для имени |
| `MX` | почтовые серверы домена |
| `CNAME` | псевдоним, отсылающий к другому имени |
| `TXT` | произвольный текст; используется для проверки владения доменом |

Из Python простейший запрос, разрешающий имя, делается одной строкой.

```python
import socket

ip_address = socket.gethostbyname("example.com")
```

DNS остаётся самым частым источником загадочных жалоб «ничего не работает». Прежде чем искать ошибку в написанной тобой программе, проверь командой `dig example.com` или `nslookup example.com`, разрешается ли имя вообще.

### URL: адрес ресурса

Адрес, вбиваемый в браузер, устроен по единой схеме.

```text
протокол://хост:порт/путь?запрос#якорь
   https :// api.example.com : 443 /v1/data ?limit=10 #results
```

Каждая часть говорит своему уровню: протокол определяет, как разговаривать, хост разрешается через DNS в IP-адрес, порт указывает транспортному уровню программу, слушающую на сервере, путь и параметры запроса адресуют конкретный ресурс, а якорь вообще не уходит на сервер и нужен только браузеру, чтобы прокрутить страницу к нужному месту.

Схем придумано много, и не все они про веб: `https://api.example.com/v1/data`, `ftp://ftp.example.com/files`, `mailto:user@example.com`.

### HTTP: как устроен разговор с сервером

На HTTP держится почти всё сетевое взаимодействие программ. Устроен он предельно просто: клиент шлёт текстовый запрос, а сервер отвечает текстовым ответом. Никакого состояния между запросами протокол не хранит, и каждый отправленный запрос самодостаточен.

#### HTTP-запрос

Запрос представляет собой обычный текст, читаемый глазами. Первая строка говорит, что и откуда мы хотим взять, дальше идут посланные заголовки, пары «имя: значение», уточняющие подробности:

```
GET /index.html HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
Connection: keep-alive
```

Первое слово отправленного запроса называется **методом** и говорит серверу, что мы хотим сделать с запрашиваемым ресурсом:

| Метод | Действие |
|---|---|
| `GET` | получить ресурс; ничего не меняет на сервере |
| `POST` | отправить данные, создать новый ресурс |
| `PUT` | заменить ресурс целиком |
| `PATCH` | изменить часть ресурса |
| `DELETE` | удалить ресурс |

Разделение, проведённое так, не формальность. `GET` считается безопасным и повторяемым, поэтому полученный результат разрешено кешировать, а сам запрос повторять при обрыве связи. С `POST` так нельзя: повторённый запрос создаст вторую запись.

#### Ответ сервера

Ответ, присланный сервером, устроен так же и содержит статусную строку, заголовки и тело:

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234
Server: nginx
Date: Mon, 21 Nov 2022 00:18:53 GMT
```

Трёхзначный код, стоящий в первой строке, остаётся самым информативным, что есть в ответе. Достаточно запомнить значение, закреплённое за первой цифрой:

| Код | Смысл | Типичные представители |
|---|---|---|
| `1xx` | информационные | 100 Continue |
| `2xx` | всё получилось | 200 OK, 201 Created |
| `3xx` | перенаправление или ответ из кеша | 301 Moved Permanently, 304 Not Modified |
| `4xx` | ошибся клиент | 404 Not Found, 401 Unauthorized, 429 Too Many Requests |
| `5xx` | ошибся сервер | 500 Internal Server Error, 503 Service Unavailable |

Различие между `4xx` и `5xx` важно на практике. В первом случае повторять отправленный запрос бессмысленно, пока не исправишь его сам; во втором есть смысл подождать и попробовать снова.

### Работа с HTTP в Python

Один раз запрос стоит собрать руками: тогда становится видно, что за словом «протокол» скрывается текст, отправленный в открытое TCP-соединение. Всё остальное время пользуются готовой библиотекой.

#### Использование сокетов

Открываем сокет, пишем в него две строки запроса, читаем присланный ответ.

```python
import socket

# TCP-соединение
with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sock:
    sock.connect(('example.com', 80))
    request = b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n'
    sock.sendall(request)
    response = sock.recv(4096)
```

Дальше начинается работа, заниматься которой обычно и не хочется. Надо найти конец заголовков, разобрать кодировку, дочитать тело по `Content-Length`, обработать присланный редирект. Одного взгляда на перечисленное хватает, чтобы взять готовое.

#### Библиотека requests

`requests` берёт на себя всю рутину: соединения, редиректы, кодировки и разбор пришедшего JSON.

```python
import requests

response = requests.get('https://api.example.com/data')
print(response.status_code)
print(response.headers)
print(response.json())
```

В коде, работающем ночью без присмотра, к этому добавляют две вещи. Первая — `timeout=` у каждого запроса: без него зависший сервер остановит сбор данных навсегда, и утром ты найдёшь программу там же, где оставил. Вторая — повтор с нарастающей паузой при ошибках `5xx`, потому что временный отказ сервера не повод терять всю ночь работы.

### TLS: буква S в HTTPS

Обычный HTTP передаёт всё открытым текстом, включая пароли и токены. Любой узел, стоящий на пути, видит содержимое. **TLS** (прежде называвшийся SSL) добавляет к соединению шифрование и проверку подлинности сервера по предъявленному сертификату, а браузер убеждается в разговоре с тем самым сайтом, за который тот себя выдаёт.

В Python шифрование добавляется обёрткой, надетой поверх обычного сокета.

```python
import ssl
import socket

context = ssl.create_default_context()
with socket.create_connection(('example.com', 443)) as sock:
    with context.wrap_socket(sock, server_hostname='example.com') as ssock:
        ssock.sendall(b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n')
        response = ssock.recv(4096)
```

## Веб-скрапинг и парсинг HTML

Не у всякого источника есть интерфейс, удобный для программ. Таблицы параметров установок, архивы наблюдений, списки публикаций и расписания смен часто существуют только как веб-страницы, и нужные данные приходится доставать разбором присланной разметки.

### Библиотека BeautifulSoup

Разбирать HTML регулярными выражениями бесполезно: разметка вложенная, а в реальной жизни ещё и битая. `BeautifulSoup` строит из скачанной страницы дерево и позволяет искать в нём по тегам и атрибутам:

```python
from bs4 import BeautifulSoup
import requests

html = requests.get('http://example.com').text
soup = BeautifulSoup(html, 'html.parser')

# Извлечение данных
title = soup.find('title').text
links = soup.find_all('a', href=True)
for link in links:
    print(link['href'], link.text)
```

### Как скрапить, не создавая проблем

Скрапинг относится к занятиям, где легко навредить и себе, и чужому серверу. Несколько правил, соблюдать которые стоит:

1. **Загляни в `robots.txt`**, файл, положенный в корень сайта, где владелец указывает, что можно обходить роботам, а что нет. Технически он ничего не запрещает, оставаясь договорённостью, но нарушать её не стоит.
2. **Делай паузы между запросами.** Сотня запросов в секунду, отправленных с одного адреса, неотличима от атаки, и тебя заслуженно заблокируют.
3. **Представляйся в заголовке `User-Agent`.** Укажи, что это за программа и как с тобой связаться; администратору, который читает логи, это сильно упрощает жизнь, а тебе снижает шанс попасть в бан.
4. **Обрабатывай ошибки.** Сеть ненадёжна, и написанный код должен переживать таймаут, `503` и внезапно изменившуюся вёрстку, а не падать посреди ночного сбора данных.
5. **Кешируй скачанное.** Повторный запуск разбора не должен снова качать уже скачанные страницы: так и быстрее, и вежливее.

И главное. Если у сайта есть API, пользуйся им, а не разбором HTML: вёрстка меняется без предупреждения, а объявленный интерфейс гораздо реже.

## Работа с API

Разбор присланной разметки остаётся крайней мерой. Если у источника есть API, разговор идёт на языке данных, а не разметки: запрос с параметрами, ответ в JSON, оговорённый набор полей вместо вёрстки, переделываемой всякий раз, когда кому-то захотелось освежить дизайн. Как сервисы договариваются между собой и что в таком договоре ломается, когда сервисов становится много, подробно разобрано у Клеппмана [16].

### Публичные API

Устроены такие интерфейсы одинаково, что бы они ни отдавали, курсы валют, переводы слов или каталог наблюдений. Всюду есть адрес сервиса, словарь передаваемых параметров и ключ доступа. Разберём на первом попавшемся из них, словаре Яндекса:

```python
import requests
import json

# Пример работы с API словаря
DICTIONARY_API = 'https://dictionary.yandex.net/api/v1/dicservice.json/lookup'
params = {
    'key': 'your_api_key',
    'lang': 'en-ru',
    'text': 'hello'
}

response = requests.get(DICTIONARY_API, params=params)
data = response.json()
translations = data['def'][0]['tr']
```

Ключ доступа служит твоим личным паролем к сервису, и в написанном коде ему не место. Держи его в переменной окружения или в конфиге, вынесенном за пределы репозитория. Второй заботой становится квота, наложенная на число запросов. Превысивший её клиент получает `429 Too Many Requests`, а при упорстве и бан по адресу, поэтому цикл по десяти тысячам записей притормаживай паузой.

### OAuth авторизация

Когда речь о твоих личных данных, простого ключа мало. **OAuth** описывает схему, при которой ты не передаёшь программе свой пароль. Вместо него сервис выдаёт ей **токен**, ограниченный по правам и по времени и отзываемый в любой момент. Полученный однажды токен дальше просто прикладывают к каждому запросу в заголовке `Authorization`:

```python
class ApiClient:
    def __init__(self, token):
        self.session = requests.Session()
        self.session.headers['Authorization'] = f'Bearer {token}'
    
    def get_user_info(self):
        response = self.session.get('https://api.example.com/user')
        return response.json()
```

Отдельно стоит `requests.Session()`. Сессия хранит выставленные заголовки между запросами и переиспользует открытое TCP-соединение, благодаря чему серия обращений к одному серверу идёт заметно быстрее, чем столько же вызовов `requests.get`, сделанных по отдельности.

### JSON формат

JavaScript Object Notation служит форматом, принятым для обмена данными: текстовым, читаемым глазами и почти один в один ложащимся на словари и списки Python.

```python
import json

# Сериализация
data = {'name': 'John', 'age': 30}
json_string = json.dumps(data)

# Десериализация
parsed_data = json.loads(json_string)
```

Одну ловушку JSON приготовил будто специально для физиков. В принятом стандарте нет ни `NaN`, ни бесконечностей. `json.dumps` выпишет их как `NaN` и `Infinity`, но это уже не JSON, и чужой разборщик на полученной строке споткнётся. Пропуски, оставшиеся в измерениях, надёжнее кодировать явным `null`.

## Асинхронные HTTP-запросы

Скачать тысячу файлов из архива по одному — значит тысячу раз подождать ответа сервера, ничем в это время не занимаясь. Почти всё время, отпущенное такой программе, съедает ожидание сети: процессор простаивает, а канал загружен на проценты от пропускаемого им. Асинхронный код позволяет держать сотню запросов в полёте одновременно и разбирать приходящие ответы по мере их поступления.

### Библиотека httpx

`httpx` повторяет интерфейс, привычный по `requests`, но умеет оба режима, синхронный и асинхронный, так что переписывать код при переходе почти не приходится:

```python
import asyncio

import httpx

# Синхронные запросы
with httpx.Client() as client:
    response = client.get('https://example.com')
    print(response.status_code)

# Асинхронные запросы
async def fetch_data():
    async with httpx.AsyncClient() as client:
        response = await client.get('https://example.com')
        return response.json()

print(asyncio.run(fetch_data()))
```

Устройство `async` и `await` подробно разбирается в главе про асинхронность; здесь важнее чувство меры. Сто запросов, запущенных одновременно, ускоряют сбор данных в десятки раз, тысяча выглядит для чужого сервера как атака. Ограничивай параллелизм явно, семафором на десяток-другой.

## Резюме

Мы прошли путь снизу вверх, от битов в кабеле до JSON в присланном ответе. Запоминать надо не столько детали протоколов, сколько саму идею слоёв: каждый уровень пользуется услугами нижнего и ничего не знает о его устройстве. Потому один и тот же код, написанный на `requests`, одинаково работает и по Wi-Fi, и по оптике.

Польза от нарисованной карты проявляется в тот момент, когда что-то не работает. Проверять уровни имеет смысл в порядке цены вопроса, а не строго снизу вверх, начиная с самого дешёвого и самого частого. Разрешение имени стоит в таблице рано по этой причине: проверяется оно одной командой, а ломается чаще прочего, хотя уровень у него прикладной.

| Что проверяем | Уровень | Чем смотреть |
|---|---|---|
| Наличие линка | физический, канальный | `ip link`, `ethtool` |
| Разрешение имени | прикладной (DNS) | `dig`, `nslookup` |
| Прохождение пакетов | сетевой | `ping`, `traceroute`, `mtr` |
| Открытый порт и слушающий его процесс | транспортный | `ss -tlnp` |
| Содержимое ответа сервера | прикладной | `curl -v`, `tcpdump` |

Порядок, выстроенный так, экономит часы: бессмысленно отлаживать код запроса, если имя сервера не разрешается, и бессмысленно смотреть в DNS, если не поднят сетевой интерфейс.

Из инструментов Python для повседневной работы достаточно двух: `requests` для обычных запросов и `httpx` там, где нужна асинхронность. Сокеты нужны не для ежедневной работы, а для понимания того, что происходит под используемыми библиотеками.
