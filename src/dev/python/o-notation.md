# Сложность операций с коллекциями

> Речь здесь о том, во что обходятся конкретные операции над списком, множеством и словарём и почему выбор структуры решает больше, чем оптимизация кода. Сама O-нотация со всей строгостью разбирается дальше, в главе [«Введение в алгоритмы»](../../cs/basic-algos.md).

Мы разобрали, какие коллекции есть в Python и как они устроены внутри. Теперь перейдём к практике и выясним, сколько стоит каждая операция и какую структуру выбрать под ту задачу, которая стоит перед тобой.

Понимание временной сложности даёт ключ к написанию эффективных программ. В нотации **O-большое**, придуманной для этого, мы описываем, как время выполнения алгоритма растёт вслед за размером входных данных, поданных ему.

## Значение сложности

Проще всего почувствовать разницу на одной строчке кода, выглядящей одинаково для двух структур, различимых только внутри. Ниже мы кладём миллион чисел в список и в множество, а потом ищем в каждом одно и то же значение оператором `in`. Синтаксис не отличается ни одним символом, а отличается работа, проделанная внутри, и разрыв, полученный на замере, впечатляет:

```python
from timeit import timeit
import random

# Сравним поиск в списке и множестве
large_list = list(range(1000000))
large_set = set(large_list)

# Ищем случайный элемент
target = random.randrange(1000000)

# Время поиска в списке (O(n))
list_time = timeit(lambda: target in large_list, number=1000)
# Время поиска в множестве (O(1))
set_time = timeit(lambda: target in large_set, number=1000)

print(f"Поиск в списке: {list_time:.4f} сек")
print(f"Поиск в множестве: {set_time:.4f} сек")
```

Разрыв получается не в разы, а на несколько порядков. Списку приходится перебирать элементы подряд, пока не найдётся нужный, и в среднем это даёт полмиллиона сравнений. Множество считает от значения хеш и сразу смотрит в ячейку, отвечающую этому хешу, обходясь одной операцией независимо от того, миллион там элементов или десять.

## Сложность операций со списками

### Константное время O(1)
```python
my_list = [1, 2, 3, 4, 5]

# Эти операции выполняются за постоянное время
my_list.append(6)      # Добавление в конец
last = my_list.pop()   # Удаление с конца
element = my_list[2]   # Доступ по индексу
length = len(my_list)  # Получение длины
```

**Почему O(1)**: список в Python устроен как динамический массив указателей. Он всегда выделяет памяти с запасом, поэтому обычный `append` просто записывает указатель в свободную ячейку и увеличивает счётчик длины, не двигая остальные элементы, лежащие рядом.

Изредка запас кончается, и списку приходится выделить больший блок памяти и скопировать туда все элементы, что стоит уже \\( O(n) \\). Но поскольку размер увеличивают кратно, перевыделения, случающиеся при переполнении, идут всё реже, и в среднем на одну операцию по-прежнему приходится константа. Сложность, которую считают таким усреднением, называют **амортизированной** \\( O(1) \\).

### Линейное время O(n)
```python
my_list = [1, 2, 3, 4, 5]

# Эти операции требуют обхода или сдвига элементов
my_list.insert(0, 0)   # Вставка в начало → сдвиг всех элементов
my_list.remove(3)      # Поиск и удаление элемента
element in my_list     # Поиск элемента
my_list.index(4)       # Поиск индекса элемента
```

**Почему O(n)**: причины у этих операций разные, но обе упираются в размер списка. При вставке в начало все элементы, стоящие следом, приходится сдвигать на одну позицию. А `in`, `remove` и `index` вынуждены идти по списку с начала, сравнивая элементы. Заранее известного места, которое отведено под значение, у массива нет.

### Медленный и быстрый код

Обе функции, написанные ниже, решают одну задачу, убирая дубликаты с сохранением порядка. Отличие в одной строке. Первая проверяет `item not in result` по списку, вторая обращается к множеству `seen`. За строкой, сидящей внутри цикла, прячется ещё один проход по всем элементам, превращающий линейный алгоритм в квадратичный.

```python
# НЕЭФФЕКТИВНО: O(n²)
def remove_duplicates_slow(data):
    result = []
    for item in data:
        if item not in result:  # O(n) для каждого элемента!
            result.append(item)
    return result

# ЭФФЕКТИВНО: O(n)
def remove_duplicates_fast(data):
    seen = set()
    result = []
    for item in data:
        if item not in seen:    # O(1) проверка!
            seen.add(item)
            result.append(item)
    return result

# Тестируем на семи тысячах случайных чисел
import random
data = [random.randrange(7000) for _ in range(7000)]

slow_time = timeit(lambda: remove_duplicates_slow(data), number=1)
fast_time = timeit(lambda: remove_duplicates_fast(data), number=1)

print(f"Медленная версия: {slow_time:.4f} сек")   # 0.0520
print(f"Быстрая версия:   {fast_time:.4f} сек")   # 0.0002
```

Разница в двести пятьдесят раз, и растёт она вместе с объёмом. На семидесяти тысячах элементов версия, написанная в лоб, отрабатывает за 4.6 секунды против 2 миллисекунд у быстрой, то есть отстаёт уже почти в две тысячи раз. Время, потраченное первой, выросло в девяносто раз при десятикратном росте данных, и это квадратичность в чистом виде.

А теперь важная тонкость про сам замер. Подставь вместо случайных чисел набор `[1, 2, 2, 3, 4, 4, 5] * 1000`, в котором те же семь тысяч элементов, и разница исчезнет. Полтора раза вместо двухсот пятидесяти. Причина в том, что **различных значений там всего пять**. Список `result`, растущий только на новых значениях, больше пяти элементов не станет, проверка `item not in result` пройдёт по пяти элементам вместо тысяч, и квадратичность просто не проявится.

Случай, разобранный тут, про измерения не меньше, чем про сложность. Алгоритм проверяют на данных, напоминающих настоящие. На неудачно подобранном наборе квадратичный код выглядит совершенно здоровым, а беда, дремлющая в нём, просыпается лишь на том наборе, который придёт из жизни.

## Сложность операций с множествами

Под множеством лежит хеш-таблица, разобранная в главе про хеш-функции, поэтому большинство операций имеют сложность O(1).

```python
my_set = {1, 2, 3, 4, 5}

# O(1) операции
my_set.add(6)           # Добавление
my_set.remove(3)        # Удаление
4 in my_set             # Проверка вхождения
len(my_set)             # Длина

# операции над двумя множествами — сложность у каждой своя
s1 = {1, 2, 3}
s2 = {3, 4, 5}
union = s1 | s2         # объединение:  O(len(s1) + len(s2))
intersection = s1 & s2  # пересечение:  O(min(len(s1), len(s2)))
difference = s1 - s2    # разность:     O(len(s1))
```

Разница здесь не умозрительная. Чтобы построить объединение, придётся пройти оба множества целиком. А для пересечения достаточно перебрать элементы **меньшего** множества и проверить каждый в большем, причём проверка, идущая по хешу, стоит константу. Поэтому пересечение множества из тысячи элементов с множеством из двух миллионов выполняется за микросекунды, а объединение, посчитанное для тех же двух, занимает на три порядка дольше.

**Интересный факт**: при массовых коллизиях хешей операции с множеством вырождаются в O(n), теряя всё своё преимущество. На практике так почти не бывает, разве что данные нарочно подобраны злоумышленником, знающим хеш-функцию.

## Сложность операций со словарями

Словари тоже построены на хеш-таблицах, поэтому всё, что делается **по ключу**, стоит O(1). Границу, разделяющую дешёвое и дорогое, важно видеть, а проходит она там, где кончается ключ. Любая операция, вынужденная посмотреть на все значения, стоит уже O(n), сколь бы коротко она ни записывалась.

```python
my_dict = {'a': 1, 'b': 2, 'c': 3}

# O(1) операции
my_dict['d'] = 4        # Вставка/обновление
value = my_dict['a']    # Доступ
del my_dict['b']        # Удаление
'a' in my_dict          # Проверка ключа

# O(n) операции
list(my_dict.keys())    # Создание списка ключей
list(my_dict.values())  # Создание списка значений
'value' in my_dict.values()  # Поиск по значениям
```

## Как вычислять сложность на практике

### Метод 1. Анализ вложенных циклов

```python
# O(n²) — квадратичная сложность
def find_pairs_quadratic(items):
    pairs = []
    for i in range(len(items)):          # O(n)
        for j in range(i + 1, len(items)):  # O(n)
            pairs.append((items[i], items[j]))  # O(1)
    return pairs

# O(n) — линейная сложность
def count_unique(items):
    seen = set()
    for item in items:                   # O(n)
        seen.add(item)                   # O(1)
    return len(seen)                     # O(1)
```

Правило простое. Перемножай сложности вложенных циклов и складывай сложности участков, идущих подряд: один цикл по всем элементам даёт \\( O(n) \\), а цикл, вложенный в цикл, \\( O(n^2) \\). Только смотри не на отступы, а на суть. Вызов `item not in some_list`, поставленный внутри цикла, — тоже скрытый вложенный цикл, хотя выглядит как одна строка.

### Метод 2. Учёт дорогостоящих операций

Вложенные циклы видно сразу, а вот вызовы библиотечных функций остаются незаметными. У каждого своя цена, которую надо знать. `sorted` стоит \\( O(n \log n) \\), `list(...)` и `sum(...)` обходятся в \\( O(n) \\), `min` и `max` тоже в \\( O(n) \\). Разбирая функцию, подставляй цены, выписанные тут, и складывай.

```python
def process_data(data):
    result = []
    
    # Сортировка: O(n log n)
    sorted_data = sorted(data)           # O(n log n)
    
    # Поиск каждого элемента: O(n) × O(log n) = O(n log n)
    for target in sorted_data:           # O(n)
        # Бинарный поиск: O(log n)
        # (предположим, что у нас есть реализация)
        index = binary_search(sorted_data, target)
        result.append(index)
    
    return result

# Общая сложность: O(n log n) + O(n log n) = O(n log n)
```

### Метод 3. Практическое измерение

Сложность можно и просто измерить, прогнав операцию на входах разного размера и посмотрев, как растёт время, потраченное на неё. Тут все новички попадают в одну ловушку, расставленную самой природой замеров. **Одну быструю операцию замерить нельзя.** Вставка в список занимает микросекунды, а разрешение таймера и случайный шум того же порядка, и вместо зависимости, ожидаемой тобой, получатся помехи. Поэтому операцию, взятую под замер, повторяют много раз, и делает это `timeit`.

```python
from timeit import timeit

print(f"{'размер':>8} {'время, мкс':>12} {'отношение':>10}")
prev = None
for size in [10_000, 20_000, 40_000, 80_000, 160_000]:
    setup = f"data = list(range({size}))"
    # вставляем и тут же удаляем, чтобы список не рос за время замера
    t = timeit("data.insert(0, -1); data.pop(0)", setup=setup, number=2000) / 2000
    ratio = f"{t / prev:.1f}x" if prev else "—"
    print(f"{size:8} {t * 1e6:12.1f} {ratio:>10}")
    prev = t
```

      размер   время, мкс  отношение
       10000          4.4          —
       20000          8.0        1.8x
       40000         15.7        2.0x
       80000         33.1        2.1x
      160000         62.0        1.9x

Вот она, линейная сложность: удвоение размера удваивает время. В самом замере важны две детали. Подготовка списка вынесена в `setup`, иначе во время, измеряемое таймером, попало бы его создание. И после каждой вставки элемент удаляется, иначе за две тысячи повторов список, растущий на каждом шаге, испортил бы всю картину.

Проделав то же самое с `append`, увидишь, что время, потраченное на вызов, не зависит от размера вовсе.

## Практические правила для выбора коллекций

### Когда использовать списки

Список остаётся выбором по умолчанию, и в большинстве случаев он правильный. Он нужен, когда важен порядок элементов и доступ по индексу, когда данные добавляются и снимаются с конца и когда значения, повторяющиеся в наборе, допустимы или даже осмысленны.

Единственное, чего список категорически не любит, — это работа с началом: `insert(0, x)` и `pop(0)`, требующие сдвига всего хвоста, стоят \\(O(n)\\) каждая. На больших данных это превращается в квадратичное время; там нужен дек, разобранный в главе про структуры данных и приспособленный к обоим концам.

### Когда использовать множества

Множество берут ради одной операции, ради проверки принадлежности. Она стоит \\(O(1)\\) против \\(O(n)\\) у списка, и на больших данных разница, накопленная за миллион проверок, решающая. Фильтрация миллиона событий по списку разрешённых идентификаторов займёт минуты, а сделанная через множество — доли секунды. Попутно множество бесплатно убирает дубликаты и умеет объединение, пересечение и разность.

Отказаться от него придётся в двух случаях. Если важен порядок, заданный при вставке, множество его не хранит. И если элементы, складываемые внутрь, нехешируемы: списки и словари в множество не положишь.

### Когда использовать словари

Словарь нужен там, где у данных есть естественный ключ, будь то имя канала, номер события или дата измерения. Поиск по ключу стоит \\(O(1)\\), поэтому словарь заменяет собой перебор списка везде, где приходится искать запись, у которой поле равно заданному значению. На нём же удобно группировать, отводя под ключ категорию, а под значение список объектов, попадающих в неё.

С версии Python 3.7 словарь сохраняет порядок, заданный вставкой, и выбирать между «быстро» и «по порядку» больше не приходится. А вот искать по *значению* словарь не умеет, и поиск, устроенный так, снова стоит \\(O(n)\\). Если он нужен часто, заведи второй словарь с обратным отображением.

### Оптимизация на практике

Почти вся оптимизация на этом уровне сводится к одному движению. Если по коллекции многократно ищут, преврати её в множество или словарь один раз до цикла. Построение множества стоит \\( O(m) \\), столько же, сколько один-единственный линейный поиск, поэтому время, уходящее на построение, окупается уже на второй итерации.

```python
# ПЛОХО: O(n²)
def find_common_elements_slow(list1, list2):
    result = []
    for item in list1:           # O(n)
        if item in list2:        # O(m) - линейный поиск!
            result.append(item)
    return result

# ХОРОШО: O(n + m)
def find_common_elements_fast(list1, list2):
    set2 = set(list2)            # O(m) - создание множества
    result = []
    for item in list1:           # O(n)
        if item in set2:         # O(1) - поиск в хеш-таблице!
            result.append(item)
    return result
```

## Некоторые правила сложности

Три вещи держи в голове всё время, пока пишешь код.

1. **O(1) < O(log n) < O(n) < O(n log n) < O(n²)** — иерархию, выписанную здесь, надо запомнить.
2. **Присматривайся к вложенным циклам**, дающим O(n²), потому что внутренний цикл часто спрятан за безобидным вызовом вроде `x in list`.
3. **Подбирай структуру под операцию**, беря множества и словари для поиска, списки для перебора, идущего подряд, и дек для работы с обоих концов.

Преждевременная оптимизация действительно вредна: подбирать константы в коде, выполняемом раз в сутки, — пустая трата времени. Но выбор структуры данных к ней не относится. От него зависит, останется программа рабочей на реальных данных или нет, и цена ошибки, сделанной здесь, не сравнима ни с чем.
