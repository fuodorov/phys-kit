# Сложность операций с коллекциями

> Речь здесь о том, во что обходятся конкретные операции над списком, множеством и словарём и почему выбор структуры решает больше, чем оптимизация кода. Сама O-нотация со всей строгостью разбирается дальше, в главе [«Введение в алгоритмы»](../../cs/basic-algos.md).

Глава о том, сколько стоит каждая операция над коллекциями Python и какую структуру выбрать под задачу.

В нотации **O-большое** описывают, как время выполнения алгоритма растёт вслед за размером входных данных.

## Значение сложности

Ниже мы кладём миллион чисел в список и в множество, а потом ищем в каждом одно и то же значение оператором `in`. Синтаксис не отличается ни одним символом, отличается работа, проделанная внутри:

```python
from timeit import timeit
import random

# Сравним поиск в списке и множестве
large_list = list(range(1000000))
large_set = set(large_list)

# Ищем случайный элемент
target = random.randrange(1000000)

# Время поиска в списке (O(n))
list_time = timeit(lambda: target in large_list, number=1000)
# Время поиска в множестве (O(1))
set_time = timeit(lambda: target in large_set, number=1000)

print(f"Поиск в списке: {list_time:.4f} сек")
print(f"Поиск в множестве: {set_time:.4f} сек")
```

Разрыв получается на несколько порядков. Списку приходится перебирать элементы подряд, пока не найдётся нужный — в среднем полмиллиона сравнений. Множество считает от значения хеш и сразу смотрит в ячейку, отвечающую этому хешу, обходясь одной операцией независимо от того, миллион там элементов или десять.

## Сложность операций со списками

### Константное время O(1)
```python
my_list = [1, 2, 3, 4, 5]

# Эти операции выполняются за постоянное время
my_list.append(6)      # Добавление в конец
last = my_list.pop()   # Удаление с конца
element = my_list[2]   # Доступ по индексу
length = len(my_list)  # Получение длины
```

**Почему O(1)**: список в Python устроен как динамический массив указателей. Он выделяет память с запасом, поэтому `append` записывает указатель в свободную ячейку и увеличивает счётчик длины, не двигая остальные элементы.

Изредка запас кончается, и списку приходится выделить больший блок памяти и скопировать туда все элементы, что стоит \\( O(n) \\). Но поскольку размер увеличивают кратно, перевыделения идут всё реже, и в среднем на одну операцию по-прежнему приходится константа. Такую усреднённую сложность называют **амортизированной** \\( O(1) \\).

### Линейное время O(n)
```python
my_list = [1, 2, 3, 4, 5]

# Эти операции требуют обхода или сдвига элементов
my_list.insert(0, 0)   # Вставка в начало → сдвиг всех элементов
my_list.remove(3)      # Поиск и удаление элемента
element in my_list     # Поиск элемента
my_list.index(4)       # Поиск индекса элемента
```

**Почему O(n)**: при вставке в начало все элементы, стоящие следом, приходится сдвигать на одну позицию. А `in`, `remove` и `index` идут по списку с начала, сравнивая элементы: заранее известного места под значение у массива нет.

### Медленный и быстрый код

Обе функции ниже убирают дубликаты с сохранением порядка. Отличие в одной строке: первая проверяет `item not in result` по списку, вторая обращается к множеству `seen`. За строкой внутри цикла прячется ещё один проход по всем элементам, превращающий линейный алгоритм в квадратичный.

```python
# НЕЭФФЕКТИВНО: O(n²)
def remove_duplicates_slow(data):
    result = []
    for item in data:
        if item not in result:  # O(n) для каждого элемента!
            result.append(item)
    return result

# ЭФФЕКТИВНО: O(n)
def remove_duplicates_fast(data):
    seen = set()
    result = []
    for item in data:
        if item not in seen:    # O(1) проверка!
            seen.add(item)
            result.append(item)
    return result

# Тестируем на семи тысячах случайных чисел
import random
data = [random.randrange(7000) for _ in range(7000)]

slow_time = timeit(lambda: remove_duplicates_slow(data), number=1)
fast_time = timeit(lambda: remove_duplicates_fast(data), number=1)

print(f"Медленная версия: {slow_time:.4f} сек")   # 0.0520
print(f"Быстрая версия:   {fast_time:.4f} сек")   # 0.0002
```

Разница в двести пятьдесят раз, и растёт она вместе с объёмом. На семидесяти тысячах элементов медленная версия отрабатывает за 4.6 секунды против 2 миллисекунд у быстрой, то есть отстаёт почти в две тысячи раз. Время первой выросло в девяносто раз при десятикратном росте данных: это квадратичность.

Тонкость про сам замер. Подставь вместо случайных чисел набор `[1, 2, 2, 3, 4, 4, 5] * 1000`, в котором те же семь тысяч элементов, и разница сократится до полутора раз вместо двухсот пятидесяти. Причина в том, что **различных значений там всего пять**. Список `result`, растущий только на новых значениях, больше пяти элементов не станет, проверка `item not in result` пройдёт по пяти элементам вместо тысяч, и квадратичность не проявится.

Алгоритм проверяют на данных, напоминающих настоящие. На неудачно подобранном наборе квадратичный код выглядит здоровым, а проблема проявляется на данных из жизни.

## Сложность операций с множествами

Под множеством лежит хеш-таблица, разобранная в главе про хеш-функции, поэтому большинство операций имеют сложность O(1).

```python
my_set = {1, 2, 3, 4, 5}

# O(1) операции
my_set.add(6)           # Добавление
my_set.remove(3)        # Удаление
4 in my_set             # Проверка вхождения
len(my_set)             # Длина

# операции над двумя множествами — сложность у каждой своя
s1 = {1, 2, 3}
s2 = {3, 4, 5}
union = s1 | s2         # объединение:  O(len(s1) + len(s2))
intersection = s1 & s2  # пересечение:  O(min(len(s1), len(s2)))
difference = s1 - s2    # разность:     O(len(s1))
```

Чтобы построить объединение, придётся пройти оба множества целиком. Для пересечения достаточно перебрать элементы **меньшего** множества и проверить каждый в большем, причём проверка по хешу стоит константу. Поэтому пересечение множества из тысячи элементов с множеством из двух миллионов выполняется за микросекунды, а объединение тех же двух занимает на три порядка дольше.

**Интересный факт**: при массовых коллизиях хешей операции с множеством вырождаются в O(n). На практике так почти не бывает, разве что данные нарочно подобраны злоумышленником, знающим хеш-функцию.

## Сложность операций со словарями

Словари тоже построены на хеш-таблицах, поэтому всё, что делается **по ключу**, стоит O(1). Любая операция, вынужденная посмотреть на все значения, стоит O(n), сколь бы коротко она ни записывалась.

```python
my_dict = {'a': 1, 'b': 2, 'c': 3}

# O(1) операции
my_dict['d'] = 4        # Вставка/обновление
value = my_dict['a']    # Доступ
del my_dict['b']        # Удаление
'a' in my_dict          # Проверка ключа

# O(n) операции
list(my_dict.keys())    # Создание списка ключей
list(my_dict.values())  # Создание списка значений
'value' in my_dict.values()  # Поиск по значениям
```

## Как вычислять сложность на практике

### Метод 1. Анализ вложенных циклов

```python
# O(n²) — квадратичная сложность
def find_pairs_quadratic(items):
    pairs = []
    for i in range(len(items)):          # O(n)
        for j in range(i + 1, len(items)):  # O(n)
            pairs.append((items[i], items[j]))  # O(1)
    return pairs

# O(n) — линейная сложность
def count_unique(items):
    seen = set()
    for item in items:                   # O(n)
        seen.add(item)                   # O(1)
    return len(seen)                     # O(1)
```

Перемножай сложности вложенных циклов и складывай сложности участков, идущих подряд: один цикл по всем элементам даёт \\( O(n) \\), а цикл, вложенный в цикл, \\( O(n^2) \\). Смотри не на отступы, а на суть: вызов `item not in some_list` внутри цикла — тоже скрытый вложенный цикл, хотя выглядит как одна строка.

### Метод 2. Учёт дорогостоящих операций

Вложенные циклы видно сразу, а вызовы библиотечных функций остаются незаметными. `sorted` стоит \\( O(n \log n) \\), `list(...)` и `sum(...)` обходятся в \\( O(n) \\), `min` и `max` тоже в \\( O(n) \\). Разбирая функцию, подставляй эти цены и складывай.

```python
def process_data(data):
    result = []
    
    # Сортировка: O(n log n)
    sorted_data = sorted(data)           # O(n log n)
    
    # Поиск каждого элемента: O(n) × O(log n) = O(n log n)
    for target in sorted_data:           # O(n)
        # Бинарный поиск: O(log n)
        # (предположим, что у нас есть реализация)
        index = binary_search(sorted_data, target)
        result.append(index)
    
    return result

# Общая сложность: O(n log n) + O(n log n) = O(n log n)
```

### Метод 3. Практическое измерение

Сложность можно измерить, прогнав операцию на входах разного размера и посмотрев, как растёт время. **Одну быструю операцию замерить нельзя.** Вставка в список занимает микросекунды, разрешение таймера и случайный шум того же порядка, и вместо зависимости получатся помехи. Поэтому операцию повторяют много раз, и делает это `timeit`.

```python
from timeit import timeit

print(f"{'размер':>8} {'время, мкс':>12} {'отношение':>10}")
prev = None
for size in [10_000, 20_000, 40_000, 80_000, 160_000]:
    setup = f"data = list(range({size}))"
    # вставляем и тут же удаляем, чтобы список не рос за время замера
    t = timeit("data.insert(0, -1); data.pop(0)", setup=setup, number=2000) / 2000
    ratio = f"{t / prev:.1f}x" if prev else "—"
    print(f"{size:8} {t * 1e6:12.1f} {ratio:>10}")
    prev = t
```

      размер   время, мкс  отношение
       10000          4.4          —
       20000          8.0        1.8x
       40000         15.7        2.0x
       80000         33.1        2.1x
      160000         62.0        1.9x

Линейная сложность: удвоение размера удваивает время. В замере важны две детали. Подготовка списка вынесена в `setup`, иначе в измеряемое время попало бы его создание. И после каждой вставки элемент удаляется, иначе за две тысячи повторов растущий список испортил бы картину.

Проделав то же самое с `append`, увидишь, что время вызова не зависит от размера.

## Практические правила для выбора коллекций

### Когда использовать списки

Список — выбор по умолчанию. Он нужен, когда важен порядок элементов и доступ по индексу, когда данные добавляются и снимаются с конца и когда повторяющиеся значения допустимы или осмысленны.

Список плохо переносит работу с началом: `insert(0, x)` и `pop(0)`, требующие сдвига всего хвоста, стоят \\(O(n)\\) каждая. На больших данных это превращается в квадратичное время; там нужен дек, разобранный в главе про структуры данных и приспособленный к обоим концам.

### Когда использовать множества

Множество берут ради проверки принадлежности. Она стоит \\(O(1)\\) против \\(O(n)\\) у списка. Фильтрация миллиона событий по списку разрешённых идентификаторов займёт минуты, а через множество — доли секунды. Попутно множество убирает дубликаты и умеет объединение, пересечение и разность.

Множество не подходит в двух случаях: если важен порядок вставки, множество его не хранит; и если элементы нехешируемы: списки и словари в множество не положишь.

### Когда использовать словари

Словарь нужен там, где у данных есть естественный ключ, будь то имя канала, номер события или дата измерения. Поиск по ключу стоит \\(O(1)\\), поэтому словарь заменяет перебор списка везде, где приходится искать запись, у которой поле равно заданному значению. На нём же удобно группировать, отводя под ключ категорию, а под значение список объектов, попадающих в неё.

С версии Python 3.7 словарь сохраняет порядок вставки. Искать по *значению* словарь не умеет: такой поиск стоит \\(O(n)\\). Если он нужен часто, заведи второй словарь с обратным отображением.

### Оптимизация на практике

Если по коллекции многократно ищут, преврати её в множество или словарь один раз до цикла. Построение множества стоит \\( O(m) \\), столько же, сколько один линейный поиск, поэтому оно окупается уже на второй итерации.

```python
# ПЛОХО: O(n²)
def find_common_elements_slow(list1, list2):
    result = []
    for item in list1:           # O(n)
        if item in list2:        # O(m) - линейный поиск!
            result.append(item)
    return result

# ХОРОШО: O(n + m)
def find_common_elements_fast(list1, list2):
    set2 = set(list2)            # O(m) - создание множества
    result = []
    for item in list1:           # O(n)
        if item in set2:         # O(1) - поиск в хеш-таблице!
            result.append(item)
    return result
```

## Некоторые правила сложности

1. **O(1) < O(log n) < O(n) < O(n log n) < O(n²)** — эту иерархию надо запомнить.
2. **Присматривайся к вложенным циклам**, дающим O(n²): внутренний цикл часто спрятан за вызовом вроде `x in list`.
3. **Подбирай структуру под операцию**: множества и словари для поиска, списки для последовательного перебора, дек для работы с обоих концов.

Преждевременная оптимизация вредна: подбирать константы в коде, выполняемом раз в сутки, — пустая трата времени. Но выбор структуры данных к ней не относится: от него зависит, останется программа рабочей на реальных данных или нет.
