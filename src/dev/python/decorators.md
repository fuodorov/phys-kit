# Декораторы и модуль `functools`

Одна и та же обвязка кочует из функции в функцию, будь то замер времени, запись вызова в журнал, проверка аргументов или кеширование результата. Логика везде своя, обвязка одна, а копировать её приходится в каждую, и декораторы решают ровно эту задачу, позволяя навесить поведение на функцию, не трогая её тело, написанное когда-то.

Разберём, как декоратор устроен изнутри, как передать ему аргументы, какие ловушки при этом возникают, и посмотрим на готовые декораторы, собранные в модуле `functools`.

## Синтаксис декораторов

Декоратор — это функция, принимающая другую функцию и возвращающая новую (или любой другой объект). Значок `@`, поставленный перед определением, остаётся «синтаксическим сахаром», не добавляющим никаких возможностей, зато выносит имя декоратора на видное место, прямо перед функцией.

```python
@decorator
def foo(x):
    return 42
```

Эквивалентно:

```python
def foo(x):
    return 42

foo = decorator(foo)
```

Таким образом, после применения декоратора имя `foo` будет ссылаться на результат, возвращённый вызовом `decorator(foo)`.

## Устройство простого декоратора

Разберём устройство на декораторе `trace`, печатающем каждый вызов функции. Внутри происходят три вещи, разделённые по ролям. Декоратор получает исходную функцию в `func` и определяет новую, названную `inner`; та принимает аргументы в самом общем виде `*args, **kwargs`, применимом к любой функции; наконец, `inner` делает своё дело и передаёт управление оригиналу, не забыв вернуть полученный результат. Наружу декоратор отдаёт `inner`.

```python
def trace(func):
    def inner(*args, **kwargs):
        print(func.__name__, args, kwargs)
        return func(*args, **kwargs)
    return inner
```

Заметь, что `func` остаётся доступной внутри `inner` даже после завершившейся `trace`, и это замыкание, разобранное в главе про функции.

Применим его.

```python
@trace
def identity(x):
    "I do nothing useful."
    return x

identity(42)  # Вывод: identity (42,) {} → 42
```

### Проблема атрибутов функции

У конструкции, написанной так, есть неприятный побочный эффект: после декорирования имя `identity` ссылается уже не на исходную функцию, а на `inner` со всеми её атрибутами. Документация, имя и сигнатура берутся теперь от обёртки, и человек, читающий `help`, не увидит ничего полезного.

```python
identity.__name__  # 'inner'
help(identity)     # Справка о inner, а не identity
```

Кроме неудобства при отладке, это ломает всё, что опирается на имена функций, от документации, собираемой автоматически, до фреймворков, ищущих обработчики по имени.

### Спасение через `functools.wraps`

Спасает одна строка. `functools.wraps` представляет собой декоратор, копирующий в обёртку метаданные оригинала (`__name__`, `__doc__`, `__module__`); ссылка на исходную функцию заодно кладётся в `__wrapped__`. Пишешь свой декоратор — ставь `@functools.wraps(func)` над внутренней функцией. Всегда.

```python
import functools

def trace(func):
    @functools.wraps(func)
    def inner(*args, **kwargs):
        print(func.__name__, args, kwargs)
        return func(*args, **kwargs)
    return inner
```

Теперь `identity.__name__` и `help(identity)` работают корректно, отдавая данные, взятые у оригинала.

## Декораторы с аргументами

Иногда декоратор нужно настроить, скажем указать `trace`, куда писать. Тут появляется третий уровень вложенности, сбивающий с толку всех подряд. Объясняется он просто: запись `@trace(sys.stderr)` означает два действия, а не одно. Сначала вызывается `trace(sys.stderr)`, и только полученный результат применяется к функции как декоратор, а значит, `trace` возвращает декоратор, который уже возвращает обёртку.

```python
import sys


def trace(handle):
    def decorator(func):
        @functools.wraps(func)
        def inner(*args, **kwargs):
            print(func.__name__, args, kwargs, file=handle)
            return func(*args, **kwargs)
        return inner
    return decorator

@trace(sys.stderr)
def identity(x):
    return x
```

Эквивалентно:

```python
decorator = trace(sys.stderr)
identity = decorator(identity)
```

## Декораторы с опциональными аргументами

Два декоратора, написанных выше, несовместимы по способу применения: один пишется как `@trace`, другой только как `@trace(...)`, а хочется, чтобы работали оба. Приём стандартный, и декоратор смотрит на переданное ему значение. Пришла `func` — значит, его применили без скобок и надо сразу возвращать обёртку. Пришло пусто — значит, вызов сделан со скобками, и вернуть надо декоратор, применяемый следующим шагом.

```python
def trace(func=None, *, handle=sys.stdout):
    if func is None:
        return lambda func: trace(func, handle=handle)

    @functools.wraps(func)
    def inner(*args, **kwargs):
        print(func.__name__, args, kwargs, file=handle)
        return func(*args, **kwargs)
    return inner
```

Использование:

```python
@trace
def foo(): ...

@trace(handle=sys.stderr)
def bar(): ...
```

Звёздочка, поставленная в объявлении, стоит по делу: без неё `@trace(sys.stderr)` попало бы в `func`, и декоратор принял бы файловый объект за декорируемую функцию. Требование передавать настройки только по имени убирает неоднозначность начисто.

## Полезные декораторы на практике

### Декоратор @timethis для замера времени

Первым практическим примером послужит декоратор для замера времени, выполняющий функцию `n_iter` раз и печатающий **лучший** результат, а не средний. Среднее портит любая случайная помеха вроде переключения задач, устроенного операционной системой, а минимум, выбранный из серии, показывает, на что код способен в спокойной обстановке. По той же причине в стандартной библиотеке есть `timeit.repeat`, возвращающий список замеров, из которого берут `min`. А вот сам `timeit.timeit` минимума не считает и отдаёт суммарное время всех запусков, делить которое на их число приходится самому.

```python
import time

def timethis(func=None, *, n_iter=100):
    if func is None:
        return lambda func: timethis(func, n_iter=n_iter)

    @functools.wraps(func)
    def inner(*args, **kwargs):
        print(func.__name__, end=" ... ")
        acc = float("inf")
        for i in range(n_iter):
            tick = time.perf_counter()
            result = func(*args, **kwargs)
            acc = min(acc, time.perf_counter() - tick)
        print(acc)
        return result
    return inner
```

### Декоратор @once для однократного вызова

Бывает работа, сделанная единожды и не требующая повторения, сколько бы раз функцию ни звали: чтение конфигурации, установка соединения, разбор большого справочника. `@once` запоминает результат первого вызова и дальше отдаёт сохранённое значение.

Хранить состояние декоратор мог бы в замыкании, но здесь оно положено прямо на `inner`, ведь функция тоже объект и допускает произвольные атрибуты. Плюс решения, выбранного так, в том, что флаг видно снаружи, и `some_func.called` покажет, звали функцию или нет.

```python
def once(func):
    @functools.wraps(func)
    def inner(*args, **kwargs):
        if not inner.called:
            inner.result = func(*args, **kwargs)
            inner.called = True
        return inner.result
    inner.called = False
    return inner
```

### Декоратор @memoized и мемоизация

Следующим шагом становится запоминание результата, сохранённого отдельно для каждого набора аргументов, что и называется мемоизацией. Функция ведёт словарь «аргументы → результат» и ничего не считает повторно, если ответ уже вычислен и сохранён. Ключом служит кортеж, собранный из позиционных аргументов и отсортированных именованных; сортировка нужна, чтобы `f(a=1, b=2)` и `f(b=2, a=1)` попали в одну ячейку.

```python
def memoized(func):
    cache = {}
    @functools.wraps(func)
    def inner(*args, **kwargs):
        key = args + tuple(sorted(kwargs.items()))
        if key not in cache:
            cache[key] = func(*args, **kwargs)
        return cache[key]
    return inner
```

Ограничение здесь одно: ключом словаря может быть только хешируемый объект, поэтому мемоизация, написанная так, сломается, если в функцию передать список, словарь или множество. Ради универсальности аргументы сериализуют, например через `pickle`, но тогда теряется скорость, ради которой всё и затевалось. На практике проще применять мемоизацию только к функциям с простыми аргументами и брать готовый `functools.lru_cache`, разобранный ниже.

### Декоратор @deprecated для устаревших функций

Когда функцию собираются убрать, её сначала помечают устаревшей. Она ещё работает, но при каждом вызове напоминает о себе предупреждением, выводимым в поток ошибок. Это даёт пользователям библиотеки время переписать код, завязанный на неё.

```python
import warnings

def deprecated(func):
    @functools.wraps(func)
    def inner(*args, **kwargs):
        warnings.warn(
            f"{func.__name__} устарела и будет удалена",
            category=DeprecationWarning,
            stacklevel=2,      # показать строку вызывающего кода, а не эту
        )
        return func(*args, **kwargs)
    return inner
```

Важна здесь деталь, на которой легко ошибиться: предупреждение должно выдаваться **при вызове** функции, и `warnings.warn`, помещённый внутрь `inner`, обеспечивает именно это. Соблазн вынести его в тело декоратора велик, ведь так короче, но тогда предупреждение сработает один раз при импорте модуля и больше никогда. Пользователь получит сообщение об устаревшей функции, возможно даже не вызванной им, а при настоящих вызовах не услышит ничего.

Аргумент `stacklevel=2` переводит указатель со строки, спрятанной внутри декоратора, на ту, где функцию вызвали; без него предупреждение бесполезно, поскольку место вызова по нему не найти.

Учти, что `DeprecationWarning` по умолчанию скрыт везде, кроме `__main__`. Чтобы увидеть его в своём коде, запусти интерпретатор с ключом `-W default` или добавь строку `warnings.simplefilter("always", DeprecationWarning)`.

## Контрактное программирование с декораторами

Контрактное программирование состоит в том, чтобы описывать в самой функции условия, требуемые от входа, и обещания, даваемые на выходе. Декораторы подходят для этого идеально: проверка, приписанная рядом с объявлением, видна с первого взгляда, а тело функции остаётся чистым. Напишем два, `@pre` для предусловия и `@post` для постусловия. Оба принимают проверяющую функцию и текст сообщения, а отличаются лишь тем, к чему применяется проверка: `pre` смотрит на аргументы до вызова, а `post` на результат, полученный после.

```python
def pre(cond, message):
    def decorator(func):
        @functools.wraps(func)
        def inner(*args, **kwargs):
            assert cond(*args, **kwargs), message
            return func(*args, **kwargs)
        return inner
    return decorator

def post(cond, message):
    def decorator(func):
        @functools.wraps(func)
        def inner(*args, **kwargs):
            result = func(*args, **kwargs)
            assert cond(result), message
            return result
        return inner
    return decorator
```

Использование:

```python
import math


@pre(lambda x: 0 < x < 1, "argument must be a fraction")
@post(lambda r: r < 0, "log of a fraction must be negative")
def log_fraction(x):
    return math.log(x)
```

Остаётся оговорка про `assert`, выбрасываемый из кода целиком, если интерпретатор запущен с ключом `-O`. Для контрактов внутри своей программы это то, что нужно, ведь в отладке проверяем, а в бою не платим. А вот данные, пришедшие извне, `assert`-ом проверять нельзя, там нужен явный `raise`.

## Цепочки декораторов

Декораторов, навешенных на одну функцию, может быть несколько, и порядок их важен.

```python
@deco1
@deco2
def foo(): ...
```

Читаются они снизу вверх, и ближайший к `def` применяется первым, отчего получается вот такая картина.

```python
foo = deco1(deco2(foo))
```

Значит, при вызове управление идёт в обратную сторону, сначала во внешний `deco1`, потом во внутренний `deco2` и только потом в саму функцию. Отсюда и порядок, принятый на практике: `@functools.lru_cache` ставят выше проверок, чтобы попадание в кеш не тратило время на валидацию, а `@timethis` ставят ниже, чтобы он мерил саму функцию, а не работу соседних декораторов, навешенных сверху.

## Модуль `functools`

### Мемоизация с ограничением через `lru_cache`

Готовая и куда более качественная замена нашему `@memoized`, отличающаяся от самописного варианта двумя вещами. Кеш ограничен по размеру, и при переполнении из него вытесняется запись, к которой дольше всего не обращались, — так и расшифровывается LRU, least recently used. Благодаря наложенному ограничению кеш не съедает всю память в долго живущей программе.

```python
@functools.lru_cache(maxsize=128)
def expensive_func(x):
    return x * x
```

Значение `maxsize=None` снимает наложенное ограничение, и так делают только для функций с заведомо небольшим числом различных аргументов. Метод `cache_info()` покажет число попаданий и промахов, накопленных за работу. Если попаданий почти нет, кеш только мешает. Ограничение то же, что у самописного варианта: аргументы обязаны быть хешируемыми.

### Частичное применение через `partial`

`partial` закрепляет часть аргументов и возвращает новую функцию, которой закреплённые аргументы передавать уже не нужно. Это аккуратная замена лямбде там, где надо «донастроить» готовую функцию перед передачей её куда-то дальше.

```python
f = functools.partial(sorted, key=lambda x: x[1])
f([('a', 4), ('b', 2)])  # [('b', 2), ('a', 4)]
```

### Обобщённые функции и `singledispatch`

Когда функция должна вести себя по-разному для разных типов, напрашивается лестница, набранная из `isinstance`. Она работает, но её приходится править всякий раз, когда появляется новый тип. `singledispatch` переворачивает схему, сложившуюся так: базовая функция объявляется один раз, а реализации для конкретных типов регистрируются отдельно, в том числе из другого модуля, узнавшего про базовую функцию позже.

```python
@functools.singledispatch
def pack(obj):
    raise TypeError(f"Unsupported type: {type(obj)}")

@pack.register(int)
def _(obj):
    return b"I" + hex(obj).encode("ascii")

@pack.register(list)
def _(obj):
    return b"L" + b",".join(map(pack, obj))
```

Выбор реализации идёт по типу **первого** аргумента, отсюда и «single» в названии. Имя `_`, данное зарегистрированным функциям, взято не просто так: обращаться к ним напрямую не нужно, вызывать всегда будут базовую `pack`.

### Свёртка последовательности через `reduce`

`reduce` сворачивает последовательность в одно значение, беря первые два элемента, применяя к ним функцию, а к полученному результату применяя её же со следующим элементом, и так до конца.

```python
functools.reduce(lambda acc, x: acc * x, [1, 2, 3, 4])  # 24
```

В функциональных языках это базовая конструкция, а в Python её применяют редко, ведь явный цикл читается лучше, да и для самых частых свёрток есть готовые `sum`, `min`, `max` и `any`.

## Заключение

Декораторы не сводятся к «синтаксическому сахару» — это рабочий инструмент, позволяющий добавить функции поведение, не трогая её тело, и тем самым не размазывать одну и ту же обвязку по всей программе.

Что из главы, прочитанной тобой, понадобится на практике:

- Свой декоратор всегда начинается с `@functools.wraps(func)`, поставленного над внутренней функцией.
- Декоратор с аргументами — функция, возвращающая декоратор; уровней вложенности становится три.
- Настройки декоратора делай ключевыми аргументами, иначе `@deco` и `@deco(...)` не отличить.
- В цепочке декораторов ближайший к `def` применяется первым, а при вызове срабатывает последним.
- Прежде чем писать своё, загляни в `functools`: `lru_cache`, `partial`, `singledispatch` и `total_ordering` закрывают большую часть нужд, возникающих на практике.
