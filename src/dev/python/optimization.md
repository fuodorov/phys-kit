# Почему Python не очень быстрый

Python устроен на редкость гибко, и эта самая гибкость закрывает дорогу многим оптимизациям, поскольку всякая оптимизация опирается на предположения и заранее оговорённые ограничения. Чем меньше компилятору позволено считать заранее известным, тем меньше у него простора, поэтому разберём три главные причины, заставляющие Python платить за удобство скоростью.

## 1. Динамическая типизация

Тип значения, связанного с именем, становится известен только во время исполнения, и отсюда две беды. Во-первых, интерпретатор проверяет типы на каждом шаге, и эти проверки, повторяющиеся миллионы раз, стоят времени. Во-вторых, он не знает заранее, с чем работает, и потому обязан исполнять написанный код буквально, не имея права выбросить заведомо ненужную ветку или посчитать выражение заранее.

## 2. Изменяемость всего и вся

Менять в Python можно почти всё, причём на ходу, и правке поддаются встроенные имена, тело уже определённой функции, даже локальные переменные чужого кадра стека. Ниже несколько примеров, собранных из самых наглядных случаев.


```python
import builtins

print(len("abc"))
len = lambda obj: "mock!"
print(len("abc"))
len = builtins.len
```

    3
    mock!



```python
def my_func(a, b):
    return a + b

print(my_func(1, 2))

def new_func(a, b):
    return a * b

my_func.__code__ = new_func.__code__
print(my_func(1, 2))
```

    3
    2



```python
import sys
import ctypes

def change_local_variable():
    # берём объект предыдущего кадра стека у вызывающей стороны
    frame = sys._getframe(1)
    frame.f_locals['my_var'] = "hello"
    # Force update
    ctypes.pythonapi.PyFrame_LocalsToFast(ctypes.py_object(frame),
                                          ctypes.c_int(0))

def do_smth():
    my_var = 1
    change_local_variable()
    print(my_var)

    
do_smth()
```

    hello

Приведённый пример рассчитан на Python до 3.12 включительно, поскольку начиная с 3.13
действует PEP 667. Превращённый в прокси `f_locals` пишет прямо в переменные кадра, поэтому строчки
с `ctypes` больше не нужны, а функции `PyFrame_LocalsToFast` в C API уже и нет,
и обращение к ней даст `AttributeError`. Сам фокус при этом никуда не делся,
записать в чужой кадр по-прежнему можно, только более коротким кодом.

Отсюда следует, что интерпретатор обязан выполнять написанное слово в слово. Он не может вынести проверку `i == 0` из цикла, потому что не знает, не поменяется ли `a`, `i` или сам `range` по дороге, из-за чего оптимизацию, разрешённую любому компилятору C, приходится делать руками.


```python
def do1():
    a = [-1] * 1000
    for i in range(len(a)):
        if i == 0:
            a[i] = 1
        else:
            a[i] = i
            
def do2():
    a = [-1] * 1000
    a[0] = 1
    for i in range(1, len(a)):
        a[i] = i
```


```python
%timeit -n100 do1()
%timeit -n100 do2()
```

    42.2 μs ± 970 ns per loop (mean ± std. dev. of 7 runs, 100 loops each)
    30.6 μs ± 1.14 μs per loop (mean ± std. dev. of 7 runs, 100 loops each)


## 3. CPython

Третья причина кроется в самой эталонной реализации языка, написанной очень давно.

1. CPython начинали писать задолго до многоядерных процессоров, и код, написанный тогда, успел состариться.
2. Производительность никогда не была его главной целью.
3. Приходится сохранять совместимость с C API, и это ограничение, унаследованное от прежних версий, связывает руки при изменении внутреннего устройства.

Но есть и хорошее, поскольку начиная с версии 3.11 CPython заметно ускорился, о чём рассказывают [обзор нововведений](https://docs.python.org/3/whatsnew/3.11.html#summary-release-highlights) и отдельный раздел [Faster CPython](https://docs.python.org/3/whatsnew/3.11.html#faster-cpython), посвящённый этой работе. Работа продолжается, следить за ней можно в проекте [faster-cpython](https://github.com/faster-cpython/), а отдельная линия, [Multithreaded Python without the GIL](https://docs.google.com/document/d/18CXhDb1ygxg-YXNBJNzfzZsDFosB5e6BfnXLlejd9l0/edit#), метит в ту самую глобальную блокировку, названную GIL, о которой пойдёт речь в отдельной главе.

## Когда оптимизировать

Прежде чем разбираться, как оптимизировать, стоит договориться, когда за это вообще стоит браться.

### *Premature optimization is the root of all evil*

Знаменитую фразу Кнута обычно читают так, что сначала пишем работающий код, а быстрым сделаем потом, когда функциональность готова. Звучит разумно, но следствие получается неприятное, поскольку производительность останется той, какая вышла случайно, пока кто-нибудь не наткнётся на легко исправимое место, ускоряющее написанную программу без переделки половины кода. Может повезти, а может и не повезти.

Поэтому, если тебе нужна быстрая программа, думай о скорости сразу, а прототип делай быстрым, иногда даже быстрее финальной версии. Начать с производительного решения и поддерживать его дешевле, чем надеяться разогнать написанное медленно.

Обратная крайность известна не хуже и называется «большой комок грязи», то есть архитектура, не продуманная вовсе.
```
If you think good architecture is expensive, try bad architecture.
```


Подробнее об этом написано в [эссе Фута и Йодера](http://www.laputan.org/mud/mud.html) и в [статье Википедии](https://ru.wikipedia.org/wiki/%D0%91%D0%BE%D0%BB%D1%8C%D1%88%D0%BE%D0%B9_%D0%BA%D0%BE%D0%BC%D0%BE%D0%BA_%D0%B3%D1%80%D1%8F%D0%B7%D0%B8).

### Мантра оптимизаций

1. Не делай
2. Делай это позже
3. Делай это оптимально

Противоречия с предыдущим разделом здесь нет, поскольку думать о производительности стоит с самого начала, а вот *переписывать* написанный код ради скорости следует лишь тогда, когда измерения, сделанные профилировщиком, показали, что это действительно нужно. Первый пункт — не шутка, и самой быстрой оптимизацией оказывается та, которую не пришлось делать, потому что программа и так укладывается в отведённое время.

## Как оптимизировать

> Программисты тратят чудовищно много времени, размышляя о скорости некритичных частей программы, и эти попытки ускорения оказываются вредны, если учесть отладку и сопровождение. Про мелкую эффективность надо забыть в 97 % случаев: **преждевременная оптимизация — корень всех зол**. Но нельзя упускать возможности в тех критических 3 %.
>
> *Д. Кнут, [Structured Programming with go to Statements](https://dl.acm.org/doi/10.1145/356635.356640), ACM Computing Surveys, 1974*


Главная задача состоит в том, чтобы найти место, куда стоит прикладывать усилия, и на это работают два правила, проверенных практикой.

### Правило 1. Профилируй код

Допустим, ты ускорил функцию в десять раз, вот только исполняется она в одном проценте случаев, и выигрыш, полученный такой ценой, выходит мизерным.

Гадать, какая часть написанной программы работает дольше всего, бесполезно, поскольку профилировщик отвечает на этот вопрос точно, а интуиция — почти никогда.


### Правило 2. Не забывай про корректность

Оптимизация легко ломает код, причём тихо, оставляя результат правдоподобным, но неверным. Прежде чем переписывать кусок ради скорости, покрой его тестами, иначе полученное ускорение будет не с чем сверить.

## Профилирование

Базовый набор почти весь входит в стандартную поставку. `cProfile` собирает профиль, `pstats` разбирает и сортирует собранное, а SnakeViz превращает полученный результат в картинку, открывающуюся в браузере.

Отдельно стоит знать ещё два инструмента.

1. [py-spy](https://github.com/benfred/py-spy) снимает профиль с уже запущенной программы, не требуя менять её код, и незаменим, когда расчёт идёт третьи сутки и перезапускать его никак нельзя.
2. [line_profiler](https://github.com/pyutils/line_profiler) профилирует построчно и показывает время, приходящееся на каждую строку.

## Измерение времени

Иногда полноценный профиль не нужен, надо просто замерить время одной функции, для чего в стандартной библиотеке есть модуль `timeit`, входящий в поставку.


```python
import timeit

setup = '''
s='abcdefghijklmnopqrstuvwxyz'

def reverse_0(s: str) -> str:
    reversed_output = ''
    s_length = len(s)
    for i in range(s_length-1, 0-1, -1):
        reversed_output = reversed_output + s[i]
    return reversed_output

def reverse_5(s: str) -> str:
    return s[::-1]
'''
```


```python
timeit.timeit('reverse_0(s)', setup, number=10000)
```




    0.020173080999484228




```python
timeit.timeit('reverse_5(s)', setup, number=10000)
```




    0.001456363000215788



Функция `timeit` замеряет время по `time.perf_counter`, на время измерения отключает сборщик мусора и возвращает суммарное время `N` запусков, а не усреднённое по ним.

Строки здесь появились не от хорошей жизни, поскольку внутри `timeit` устроен как [шаблонная строка](https://github.com/python/cpython/blob/master/Lib/timeit.py#L69), принимающая твои параметры, и накладные расходы на вызов функции-обёртки из замера таким образом уходят. Настоящие функции `timeit` тоже берёт, просто в замер тогда попадёт и вызов, сделанный ради них.

В IPython для того же есть магическая команда `%timeit`, выводящая, в отличие от функции, среднее время и стандартное отклонение, посчитанное по семи прогонам.


```python
def reverse_0(s: str) -> str:
    reversed_output = ''
    s_length = len(s)
    for i in range(s_length-1, 0-1, -1):
        reversed_output = reversed_output + s[i]
    return reversed_output

%timeit -n100 reverse_0('abcdefghijklmnopqrstuvwxyz')
```

    2.09 μs ± 130 ns per loop (mean ± std. dev. of 7 runs, 100 loops each)

Инструменты измерения на этом заканчиваются, и дальше начинается сама оптимизация. Следующая глава разбирает, что можно выжать из самого языка, не подключая ничего постороннего, а за ней идёт глава, разгоняющая расчёт компиляторами и векторизацией.
