# От скрипта к приложению


Почти любой код, живущий в лаборатории, рождается одинаково. Вечером перед семинаром ты пишешь `analysis.py` на пятьдесят строк: загрузить осциллограммы, вычесть базовую линию, найти пик, нарисовать график. Скрипт работает, нарисованный график попадает в отчёт, все довольны.

Дальше события развиваются по сценарию, знакомому каждому:

- через полгода в скрипте, разросшемся до 800 строк, завелись калибровка, три формата входных файлов и ветка `if experiment == "march":`;
- рядом лежат `analysis_new.py`, `analysis_final.py` и `analysis_final_v2_REAL.py`, и никто уже не помнит признаков, отличающих их друг от друга;
- пути к данным (`/home/vasya/data/2026-03-12/`) и параметры установки, зашитые в код, приходится править в исходнике перед каждым запуском;
- на другой машине скрипт не запускается, и начинается выяснение установленных версий numpy;
- приходит новый студент, и ты полчаса объясняешь, какие строки нужно закомментировать, чтобы «просто посчитать спектр».

Одноразовый скрипт остаётся нормальным жанром, стыдиться его не нужно. Проблемы начинаются, когда код, написанный на один раз, незаметно становится многоразовым. Его гоняет вся группа, на него ссылаются в опубликованных статьях, а устроен он по-прежнему как черновик.

Разница между скриптом и приложением лежит не в количестве строк, а в свойствах, перечисленных ниже:

- приложение ставится на чистую машину одной-двумя командами;
- его запускают, не открывая исходники в редакторе, и запуск описан в README;
- оно внятно сообщает об ошибках и ведёт журнал, переживающий сам запуск;
- его можно менять, не боясь незаметно сломать физику, за этим следят написанные тесты;
- в нём разберётся другой человек. Или ты сам через полгода, что почти то же самое.

В главе про [жизненный цикл ПО](./life.md) мы смотрели на разработку с высоты птичьего полёта. Здесь спустимся на землю и пройдём путь целиком на примере, тянущемся через всю главу, превратив скрипт обработки осциллограмм в пакет `beamtool`, которым сможет пользоваться вся группа.

В примерах ниже встретится NumPy: `loadtxt` читает таблицу чисел из файла, `argmax` возвращает индекс максимума, `trapezoid` считает интеграл методом трапеций. Устройство массивов разбирается дальше, в главе [«NumPy и pandas»](python/numpy-and-pandas.md); здесь важна не библиотека, а обвязка вокруг неё.

## Структура проекта

Начнём с механики. Любой файл `.py` служит *модулем*, пригодным для импорта. Каталог, содержащий файл `__init__.py`, называют *пакетом*, набором модулей, объединённых общим именем. Как только код перестаёт помещаться в один файл, разложи его по модулям, разделённым по смыслу: чтение данных отдельно, формулы отдельно, графики отдельно. На один модуль приходится одна зона ответственности.

Структура, сложившаяся как типовая, выглядит так:

```text
beamtool/                  # корень git-репозитория
├── pyproject.toml         # метаданные проекта и зависимости
├── README.md              # что это, как поставить, как запустить
├── .gitignore
├── configs/
│   └── default.toml       # параметры обработки по умолчанию
├── src/
│   └── beamtool/          # сам пакет
│       ├── __init__.py
│       ├── io.py          # чтение и запись данных
│       ├── physics.py     # формулы и численные методы
│       ├── plotting.py    # вся работа с matplotlib
│       └── cli.py         # интерфейс командной строки
└── tests/
    ├── test_io.py
    └── test_physics.py
```

Это так называемый *src-layout*, при котором пакет спрятан в каталоге `src/`. Есть и плоский вариант (flat layout), где `beamtool/` лежит прямо в корне репозитория; для маленьких проектов годится и он. Преимущество src-layout в том, что пакет, спрятанный от рабочего каталога, нельзя случайно импортировать минуя установку, и тесты проверяют ровно то, что получит пользователь.

Отдельно стоит решить, где живут обрабатываемые данные. Сырые данные, снятые на установке, в репозиторий не кладут. Git плохо переносит гигабайты бинарников, а история изменений, накопленная для них, бессмысленна. Данные лежат на сервере или дисках группы, а в репозитории остаются путь к ним, записанный в конфиге, и маленькие файлы-образцы для тестов (`tests/data/`). Каталоги `data/`, `.venv/`, `__pycache__/` и файлы `*.log` добавь в `.gitignore` сразу, не дожидаясь первого коммита, случайно унёсшего в историю два гигабайта.

## Виртуальные окружения и зависимости

Системный Python работает как общая кухня. В ней готовят все программы, установленные на машине, и обновление библиотеки, сделанное ради одного проекта, ломает другой. Поэтому у каждого проекта должно быть своё *виртуальное окружение* — набор пакетов, изолированный от системного.

```bash
cd beamtool
python -m venv .venv
source .venv/bin/activate    # в Windows: .venv\Scripts\activate
pip install numpy matplotlib
```

Окружение служит расходным материалом: сломанное или запутавшееся удаляешь вместе с каталогом `.venv` и создаёшь заново за минуту. Но работает это, только если список зависимостей хранится в репозитории, а не в твоей голове. Способов записать его два.

Классический способ опирается на файл `requirements.txt`, простой список, скармливаемый `pip install -r requirements.txt`.

```text
numpy==2.1.3
matplotlib==3.9.2
```

Современный способ использует секцию `dependencies` в `pyproject.toml`, едином файле с метаданными проекта, разбираемом ниже в разделе про упаковку. Для нового проекта выбирай `pyproject.toml`; `requirements.txt` останется тебе как точный слепок собранного окружения.

Теперь про закрепление версий. Режимов, применяемых на практике, здесь два. В библиотеке, которую ставят другие, версии ограничивают мягко (`numpy>=2.0`), чтобы не конфликтовать с чужими зависимостями. В приложении для обработки данных важнее воспроизводимость. Команда `pip freeze > requirements.txt` фиксирует всё окружение до последней цифры, и через год ты сможешь пересоздать его и повторить расчёт, опубликованный в статье. Обновление той же scipy иногда меняет численные результаты в последних знаках, а для науки это повод зафиксировать версии намертво.

Вместо связки venv + pip можно взять современный менеджер проектов, [poetry](https://python-poetry.org/) или [uv](https://docs.astral.sh/uv/). Они делают то же самое, то есть окружение, зависимости и lock-файл с точными версиями, но одной командой и с автоматическим разрешением конфликтов; uv, написанный на Rust, к тому же работает на порядок быстрее pip. Начни с venv и pip, чтобы понимать механику, а на менеджеры перейдёшь, когда почувствуешь, какую рутину они убирают у привыкшего к ним человека.

## Точки входа

Модуль должен переживать импорт без побочных эффектов, поэтому при `import beamtool.cli` ничего не должно считаться, рисоваться и попадать на диск. Исполняемый код закрывается конструкцией, ставшей стандартной:

```python
if __name__ == "__main__":
    main()
```

Переменная `__name__` равна `"__main__"` только у файла, запущенного как программа, а не импортированного. Это уже было в наших требованиях к коду; теперь сделаем следующий шаг к интерфейсу командной строки, устроенному по-человечески, чтобы параметры передавались аргументами, а не правкой исходника. В стандартной библиотеке для этого есть модуль `argparse`:

```python
"""Интерфейс командной строки beamtool."""

import argparse
from pathlib import Path

import numpy as np


def parse_args() -> argparse.Namespace:
    """Разбирает аргументы командной строки."""
    parser = argparse.ArgumentParser(
        prog="beamtool",
        description="Обработка осциллограмм: базовая линия, пик, заряд.",
    )
    parser.add_argument(
        "--input", type=Path, required=True,
        help="входной CSV-файл с колонками time, voltage",
    )
    parser.add_argument(
        "--output", type=Path, required=True,
        help="файл для записи результатов",
    )
    parser.add_argument(
        "--plot", action="store_true",
        help="показать график после обработки",
    )
    parser.add_argument(
        "--baseline-points", type=int, default=100,
        help="сколько первых точек считать базовой линией",
    )
    return parser.parse_args()


def main() -> None:
    """Точка входа приложения."""
    args = parse_args()
    time, voltage = np.loadtxt(
        args.input, delimiter=",", skiprows=1, unpack=True)

    # Базовая линия — среднее по первым точкам до прихода сигнала.
    baseline = voltage[:args.baseline_points].mean()
    signal = voltage - baseline
    peak_index = int(np.argmax(signal))
    area = float(np.trapezoid(signal, time))

    np.savetxt(
        args.output,
        [[time[peak_index], signal[peak_index], area]],
        delimiter=",",
        header="peak_time,peak_voltage,area",
    )

    if args.plot:
        # Ленивый импорт: без --plot matplotlib даже не загружается,
        # и скрипт работает на сервере без дисплея.
        from beamtool.plotting import show_signal
        show_signal(time, signal, peak_index)


if __name__ == "__main__":
    main()
```

Запуск теперь выглядит так: `python -m beamtool.cli --input shot_042.csv --output results.csv --plot`. Команда заработает после того, как пакет установлен в окружение (`pip install -e .`, см. раздел про упаковку); до установки при src-layout запускай `PYTHONPATH=src python -m beamtool.cli …`. Бесплатно к этому прилагается `--help`, поскольку argparse сам генерирует справку, проверяет обязательные аргументы и приводит типы к объявленным. Пользователю больше не нужно открывать код, а значит, и случайно сломать написанное он не сможет.

Для разросшихся интерфейсов с подкомандами (как `git commit`, `git push`) есть сторонние библиотеки [click](https://click.palletsprojects.com/) и [typer](https://typer.tiangolo.com/), делающие то же самое декораторами и аннотациями типов. Но argparse, входящего в стандартную библиотеку, хватает надолго, и он всегда под рукой.

## Конфигурация

Магические числа и пути, вписанные в код, остаются главным источником хаоса в лабораторных скриптах. Порог дискриминатора, частота дискретизации АЦП, путь к данным меняются от запуска к запуску, и, зашитые в исходник, они требуют правки кода при каждом запуске. История в git превращается в мусор из «поменял порог обратно», а воспроизводимость умирает, потому что никто не помнит, с какими параметрами получен график, ушедший в статью.

Правило, разделяющее их, простое. Код отвечает на вопрос «как считать», конфигурация — на вопрос «что и с какими параметрами». Вынесенные параметры складывают в конфиг-файл, а удобным форматом служит TOML, читаемый стандартной библиотекой (Python 3.11+).

```toml
# configs/default.toml

[detector]
sampling_rate_hz = 2.5e9   # частота дискретизации АЦП
impedance_ohm = 50.0

[analysis]
baseline_points = 100      # точек на оценку базовой линии
peak_threshold_v = 0.05    # порог отбора событий
```

```python
import tomllib

with open("configs/default.toml", "rb") as f:
    config = tomllib.load(f)

threshold = config["analysis"]["peak_threshold_v"]
```

YAML устроен так же по духу (нужен пакет `pyyaml`); выбери один формат из двух и держись выбранного. Конфиг, положенный в репозиторий, версиями в git образует историю твоих параметров обработки. Видно, кем, когда и на сколько сдвинут любой порог.

Для того, что зависит от конкретной машины или должно оставаться секретным, используют переменные окружения:

```python
import os

data_dir = os.environ.get("BEAMTOOL_DATA_DIR", "/data/beam")
```

Пароли и токены, например доступ к базе данных группы (о них в главе про базы данных), никогда не попадают ни в код, ни в git. Только переменные окружения или локальный файл `.env`, добавленный в `.gitignore`. Приоритет источников, сложившийся как общепринятый, обычно такой: значения по умолчанию → конфиг-файл → переменные окружения → аргументы командной строки; каждый следующий уровень перекрывает предыдущий.

## Логирование вместо print

`print` хорош для отладки, занимающей две минуты. Дальше начинаются проблемы: отладочный вывод, разбросанный по коду, нельзя отключить, не вырезая его; у сообщений нет ни времени, ни важности; всё уходит в консоль и исчезает вместе с закрытым окном. А когда ночная обработка падает на 3742-м файле из 5000, тебе нужен журнал, сохранивший, что происходило, с какими файлами и когда.

Всё это умеет `logging`, входящий в стандартную библиотеку. У сообщений есть пять уровней (`DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`) и глобальный порог, решающий, что показывать. Настройка, пишущая одновременно в консоль и в файл, выглядит так:

```python
import logging

logger = logging.getLogger(__name__)


def setup_logging(logfile: str = "beamtool.log") -> None:
    """Включает вывод логов в консоль и в файл одновременно."""
    logging.basicConfig(
        level=logging.INFO,
        format="%(asctime)s %(levelname)-8s %(name)s: %(message)s",
        handlers=[
            logging.StreamHandler(),
            logging.FileHandler(logfile, encoding="utf-8"),
        ],
    )
```

Использование в коде:

```python
logger.info("Загружен файл %s: %d точек", path, n_points)
logger.warning("Пик ниже порога %.3f В, файл пропущен", threshold)
logger.error("Не удалось разобрать файл %s", path, exc_info=True)
```

Три детали, стоящие внимания. `getLogger(__name__)` в каждом модуле даёт по именованному логгеру, и в записанном журнале видно, какой модуль пишет. Флаг `--verbose` в CLI может опускать порог до `DEBUG`, не трогая код; отладочные сообщения, записываемые всегда, показываются по требованию. А `exc_info=True` добавляет к сообщению полный traceback, так что утром ты увидишь не только «файл пропущен», но и почему.

## Обработка ошибок

Главный принцип научного кода называется *fail fast*. Обнаружил некорректные данные, падай сразу и громко. Альтернатива, кажущаяся мягче, страшнее падения. Тихий NaN проползает через все стадии обработки и превращается в правдоподобный, но неверный график. Упавшую программу чинят; красивую кривую с ошибкой отправляют в статью.

Python сообщает об ошибках исключениями, и ты можешь определять свои, обычные классы, наследуемые от `Exception`.

```python
import numpy as np


class BeamtoolError(Exception):
    """Базовый класс ошибок beamtool."""


class InvalidSignalError(BeamtoolError):
    """Сигнал не пригоден для обработки."""


def find_peak(signal: np.ndarray) -> int:
    """Возвращает индекс максимума сигнала."""
    if signal.size == 0:
        raise InvalidSignalError("пустой сигнал")
    if not np.all(np.isfinite(signal)):
        raise InvalidSignalError("в сигнале есть NaN или inf")
    return int(np.argmax(signal))
```

Свои классы отделяют *ожидаемые* ошибки от багов. На верхнем уровне, в `main()`, ты ловишь `except BeamtoolError`, и кривой файл, попавшийся в пачке из тысячи, оказывается штатной ситуацией, записал в журнал и пошёл к следующему. А `KeyError` или `TypeError` означают баг в твоём коде; он должен пролететь наружу с полным traceback, чтобы его починили, а не спрятали.

Худшее, что можно сделать с пойманным исключением, — это проглотить его:

```python
# Так делать нельзя: ошибка исчезает бесследно,
# а в результатах молча появляется дыра.
try:
    result = process(path)
except Exception:
    pass
```

Правило простое. Лови исключение только там, где знаешь, что делать с пойманным, а во всех остальных местах не лови вовсе.

## Тесты

Научному коду тесты нужны даже больше, чем сайтам и мессенджерам. Главный риск здесь не в том, что «программа упала», а в том, что «программа выдала правдоподобное, но неверное число». Особенно коварны рефакторинги формул. Ты «слегка упростил» выражение, потерял двойку в знаменателе, и все посчитанные результаты уехали, а код по-прежнему работает без единой ошибки. Тесты фиксируют записанное поведение, и любое изменение, сдвинувшее численный результат, всплывает немедленно. Это и есть защита от регрессий.

Стандартом де-факто служит [pytest](https://docs.pytest.org/), где тесты лежат в `tests/test_*.py`, называются `test_*` и состоят из обычных `assert`. Возьмём функцию из `beamtool`:

```python
# src/beamtool/physics.py

ELECTRON_REST_ENERGY_MEV = 0.511


def lorentz_gamma(kinetic_energy_mev: float) -> float:
    """Возвращает лоренц-фактор по кинетической энергии электрона."""
    if kinetic_energy_mev < 0:
        raise ValueError("кинетическая энергия отрицательна")
    return 1.0 + kinetic_energy_mev / ELECTRON_REST_ENERGY_MEV
```

И тесты к ней:

```python
# tests/test_physics.py

import pytest

from beamtool.physics import lorentz_gamma


def test_gamma_at_rest():
    # Покоящийся электрон: гамма-фактор равен единице.
    assert lorentz_gamma(0.0) == pytest.approx(1.0)


def test_gamma_one_mev():
    assert lorentz_gamma(1.0) == pytest.approx(2.9569, abs=1e-4)


def test_negative_energy_rejected():
    with pytest.raises(ValueError):
        lorentz_gamma(-1.0)
```

Команда `pytest`, запущенная в корне проекта, сама найдёт и прогонит все тесты. Отдельно про `pytest.approx`. Сравнивать float через `==` нельзя из-за ошибок округления, накапливающихся в последних знаках, а `approx` сравнивает с заданным допуском, абсолютным (`abs=`) или относительным (`rel=`).

В первую очередь тестируют функции-формулы на входах с заранее известным ответом (аналитические пределы, симметрии, законы сохранения), парсеры форматов данных на файлах-образцах, положенных в `tests/data/`, граничные случаи (пустой сигнал, один отсчёт, отрицательная энергия). Для численных методов хорош такой ход: прогнать решатель на упрощённой задаче, имеющей аналитическое решение, и сравнить. Написанный один раз тест проверяет каждый следующий рефакторинг бесплатно.

## Типизация

Аннотации типов, расставленные во всех примерах выше, ты уже видел:

```python
def rebin(spectrum: np.ndarray, factor: int = 2) -> np.ndarray:
    """Огрубляет спектр, суммируя соседние каналы."""
    n_bins = spectrum.size // factor * factor
    return spectrum[:n_bins].reshape(-1, factor).sum(axis=1)
```

Во время выполнения Python их не проверяет: аннотации остаются документацией, читаемой машиной, не более. Зато её понимают инструменты, читающие исходник. Редактор подсказывает атрибуты и ловит опечатки, а статический анализатор [mypy](https://mypy.readthedocs.io/) командой `mypy src/` находит несостыковки до запуска: сюда передали `str` вместо `Path`, там функция может вернуть `None`, а вызывающий код об этом не знает. Для расчёта, идущего три часа, пойманная за секунду до запуска ошибка означает большую экономию жизни. Аннотируй хотя бы функции, вынесенные в публичный интерфейс пакета, и добавь mypy в CI рядом с линтерами.

## Документация

Минимальный набор документации, требуемый от проекта, у тебя уже почти есть. Docstring у каждой публичной функции говорит, что она делает, что принимает, что возвращает и в каких единицах (перепутанные мэВ и МэВ не поймает ни один тайпчекер). README в корне репозитория отвечает на три вопроса: что это за проект, как его поставить, как запустить, и снабжается одним работающим примером команды; это первое, что увидит коллега, и часто единственное прочитанное им. Когда проект вырастает, из docstring'ов и markdown-файлов собирают сайт документации при помощи [mkdocs](https://www.mkdocs.org/) или [sphinx](https://www.sphinx-doc.org/); собранная документация при этом живёт в том же репозитории и обновляется вместе с кодом, а не в отдельном вордовском файле на сетевом диске.

## Упаковка и распространение

Осталось собрать написанное воедино. Центральным файлом современного Python-проекта служит `pyproject.toml`.

```toml
[project]
name = "beamtool"
version = "0.1.0"
description = "Обработка осциллограмм с датчиков пучка"
requires-python = ">=3.11"
dependencies = [
    "numpy>=2.0",
    "matplotlib>=3.9",
]

[project.scripts]
beamtool = "beamtool.cli:main"

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"
```

Теперь проект можно установить в окружение в режиме разработки:

```bash
pip install -e .
```

Флаг `-e` (editable) ставит пакет «ссылкой» на рабочий каталог, и внесённые правки видны сразу, без переустановки. После установки заработают импорты `from beamtool.physics import ...` из любого места, в том числе из тестов. А секция `[project.scripts]` создаёт в окружении настоящую консольную команду, и функция `main()` из `cli.py` теперь вызывается просто как `beamtool --input shot_042.csv --output results.csv`.

Распространение идёт по нарастающей, ступенями. Коллегам из группы достаточно git-репозитория, из которого `pip install git+https://github.com/mygroup/beamtool` ставит пакет со всеми объявленными зависимостями. Команда `python -m build` собирает из проекта wheel-файл в `dist/`, который можно приложить к релизу на GitHub или передать на машину без интернета. Публикация на [PyPI](https://pypi.org/) через `twine upload` (или `uv publish`) становится финальной ступенью, когда инструментом хотят пользоваться незнакомые тебе люди; для внутренних инструментов группы она не обязательна.

## Когда приложение вырастает в систему

Всё, сказанное выше, относится к одному инструменту, делающему одну вещь. Рано или поздно появляется задача, которую одним инструментом не закрыть, например провести эксперимент целиком. Выставить токи магнитов, дождаться стабилизации, снять показания с десятка датчиков, посчитать результат, решить, куда двигаться дальше, повторить, и всё это сотни раз подряд, ночью, без человека у пульта.

Такую программу уже нельзя писать «плоско». Разберём, как устроена библиотека SCAUT, оркеструющая эксперименты на линейном ускорителе инжектора ЦКП «СКИФ». Она согласованно управляет всеми компонентами установки, от магнитов до детекторов.

Ключевая идея состоит в **разделении на слои**, где каждый слой знает только о соседнем:

```
Интерфейс эксперимента   что именно сканируем и в каких пределах
        │
Управление сканированием планировщик точек, обработчики событий, обработка аварий
        │
Абстракция оборудования  «мотор» и «датчик» — независимо от того, что за железо
        │
Коммуникация             EPICS, Tango, OPC UA — или расчётная модель вместо железа
        │
Данные                   сериализация, метаданные эксперимента, хранилище
        │
Анализ                   визуализация, статистика, постобработка
```

Разберём, что даёт каждая из проведённых границ.

Самой ценной из них оказывается **абстракция оборудования**. Верхние слои оперируют понятиями «мотор» (нечто, принимающее заданное значение) и «датчик» (нечто, у чего значение можно спросить). Что стоит за мотором, источник питания квадруполя, шаговый двигатель экрана или регулятор фазы СВЧ, процедуре сканирования безразлично. Добавление нового прибора не требует правок в написанной логике эксперимента. Пишется новый адаптер, и всё, написанное выше него, остаётся нетронутым.

Ниже лежит **слой коммуникации**, отделяющий протокол от смысла. Ускорительными комплексами управляют разные системы, EPICS, Tango, OPC UA, и код эксперимента не должен знать, какая из них стоит внизу под ним. Но интереснее другое. На место реального железа можно подставить расчётную модель. Тот же самый сценарий эксперимента, не изменённый ни в одной строке, прогоняется сначала на модели пучка, а потом на установке. Ошибка в логике сканирования обнаруживается на модели, где она стоит ноль, а не в смену, где она стоит пучкового времени всей группы.

Наконец, за то, чтобы результат пережил эксперимент, отвечает **слой данных**. Кроме собственно измерений сохраняются метаданные, описывающие, когда, кем, при каких настройках и какой версией кода они сняты. Без этого через полгода из архива нельзя будет извлечь ничего, кроме массива чисел неизвестного происхождения.

Процедура сканирования при этом всегда проходит одни и те же шесть этапов:

1. **Инициализация**. Проверить, что нужное оборудование на связи, выставить начальные параметры.
2. **Планирование**. Построить последовательность точек в пространстве параметров.
3. **Выполнение**. На каждом шаге выставить параметры и снять данные.
4. **Обработка событий**. Вызвать пользовательские функции анализа.
5. **Сериализация**. Сохранить результаты и метаданные.
6. **Завершение**. Освободить ресурсы, сформировать отчёт.

Первый и последний пункты выглядят формальностью до первого ночного прогона, упавшего на середине. Не проверила инициализация связь с прибором, и эксперимент честно отработает четыре часа, записав в файл одни нули. А если завершение не освободило ресурсы, следующий запуск просто не подключится к оборудованию, потому что предыдущий процесс, так и не завершившийся, всё ещё держит соединение.

Из разобранного примера бери принцип. **Границы проводят там, где ожидаются изменения.** Оборудование, стоящее на установке, меняется, поэтому нужен слой его абстракции. Протоколы управления в разных лабораториях разные, отсюда отдельный слой коммуникации. Чаще всего меняется способ анализа данных, и потому анализ, отделённый от сбора, можно переписывать, не трогая ничего остального. А вот слой, за которым ничего никогда не меняется, только мешает, и вводить его «на будущее» не нужно.

## Чек-лист: скрипт стал приложением

Проверь свой проект по списку, приведённому ниже:

- [ ] Код разложен по модулям со смыслом: ввод-вывод, физика, графика, CLI.
- [ ] Проект ставится на чистую машину командами `git clone` и `pip install -e .`.
- [ ] Зависимости с версиями записаны в `pyproject.toml`, точный слепок собранного окружения можно получить и восстановить.
- [ ] Запуск не требует открывать исходники, все параметры передаются через аргументы CLI и конфиг-файл.
- [ ] Пути, калибровки и пороги живут в конфиге, а не в коде; секретов в репозитории нет.
- [ ] Вместо `print` используется `logging`, и после ночного прогона остаётся журнал, размеченный временем и уровнями.
- [ ] Некорректные данные вызывают внятную ошибку сразу, а не тихий NaN, всплывающий в результатах.
- [ ] Ключевые формулы покрыты тестами; `pytest` проходит перед каждым коммитом.
- [ ] Публичные функции аннотированы типами и снабжены docstring; `mypy` молчит.
- [ ] README отвечает на вопросы «что это», «как поставить», «как запустить».
- [ ] Файл `analysis_final_v2_REAL.py` удалён, поскольку версии живут в git, а не в именах файлов.

Не пытайся сделать всё перечисленное в первый же вечер. Структура, окружение и git нужны сразу, они почти ничего не стоят. Конфиг, логирование и CLI появляются у скрипта, запускаемого чаще раза в неделю. Тесты приходят, как только полученным результатам начинают доверять другие люди. Превращение скрипта в приложение — не событие, а привычка. Каждый раз, когда ты вытаскиваешь константу в конфиг или превращаешь пойманный баг в тест, код группы становится немного надёжнее. Про сети и хранилище результатов рассказано в следующих главах, а про то, как поднять свой сервис, — в главе про асинхронность.
