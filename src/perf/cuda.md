# CUDA и вычисления на GPU

В главе [«Скорость выполнения программ»](./perf.md) мы разгоняли умножение матриц на CPU, переставляли циклы, компилировали код через Numba и Cython, а в конце вызвали NumPy и получили микросекунды вместо десятков миллисекунд, потраченных циклом, написанным в лоб. В главе про GIL выяснилось, что потоки в Python упираются в глобальную блокировку, а процессов, занятых счётом, имеет смысл держать столько, сколько ядер, то есть штук восемь-шестнадцать. Это потолок CPU.

В той же машине стоит видеокарта. У современного GPU тысячи ядер, а пиковая производительность — десятки терафлопс против единиц у процессора. Если твоя задача сводится к одной операции, повторяющейся над миллионами чисел (а в физике это почти всегда так), GPU даст ускорение в 10–100 раз. Эта глава о том, как получить это ускорение из Python.

## Зачем физику видеокарта

GPU придумали для игр: независимо посчитать цвет каждого из миллионов пикселей 60 раз в секунду. Схема «одна формула на миллионах независимых элементов» встречается не только в пикселях:

* **Моделирование частиц.** Метод частиц в ячейках (PIC), молекулярная динамика, трекинг пучка в ускорителе дают миллионы частиц, и каждая на каждом шаге двигается по уравнениям, одинаковым для всех.
* **Сеточные задачи.** Уравнения теплопроводности, Пуассона, Максвелла, Навье–Стокса, решаемые на разностных сетках: значение в каждом узле пересчитывается по шаблону, продиктованному разностной схемой.
* **Обработка данных детекторов.** Реконструкция треков, фильтрация изображений, томография сводятся к конвейерам, гоняющим однотипные операции над массивами, снятыми с детектора. Триггерные фермы, поставленные на LHC, давно считают на GPU.
* **Монте-Карло.** Транспорт излучения, генерация событий: миллионы независимых историй, разыгранных по одному алгоритму.
* **Нейросети.** Обучение сводится к миллиардам умножений матриц; без GPU глубокое обучение просто не случилось бы.

Общее у этих задач — **массовый параллелизм данных**. Много элементов, над каждым одинаковая и относительно простая работа, и элементы друг от друга почти не зависят. Под этот профиль GPU и заточен.

## Чем GPU отличается от CPU

CPU оптимизирован под **латентность**, то есть под то, чтобы выполнить одну цепочку инструкций как можно быстрее. Ради этого в ядре есть предсказатель переходов, внеочередное исполнение и большие кеши. GPU оптимизирован под **пропускную способность**, то есть под то, чтобы сделать как можно больше работы в секунду, пусть каждая операция, взятая отдельно, и потребует больше времени. Ядра простые, зато их тысячи.

|                              | CPU                                   | GPU                                        |
|------------------------------|---------------------------------------|--------------------------------------------|
| Ядер                         | 4–64 сложных                          | тысячи простых (у RTX 4090 их 16 384)         |
| Частота                      | 3–5 ГГц                               | 1–2.5 ГГц                                  |
| Логика ядра                  | предсказание переходов, внеочередное исполнение | максимально простая                |
| Скрытие задержек памяти      | большие кеши                          | тысячи нитей: пока одни ждут память, считают другие |
| Полоса памяти                | ~50–100 ГБ/с (DDR5)                   | от сотен ГБ/с до единиц ТБ/с (GDDR6X, HBM)    |
| Оптимизирован под            | латентность одной задачи              | суммарную пропускную способность           |
| Идеальная нагрузка           | ветвистая, последовательная           | однотипная над большими массивами          |

### SIMT и warp

Ядра GPU не полностью независимы. Нити (threads) исполняются группами по 32, и группа называется **warp**. Все нити warp'а в каждый момент выполняют одну и ту же инструкцию над разными данными. Модель называется SIMT (Single Instruction, Multiple Threads). От SIMD, где одна инструкция применяется к вектору данных, она отличается тем, что нить здесь — самостоятельный поток управления и может уйти по своей ветке; отсюда дивергенция, о которой ниже.

Если внутри warp'а код ветвится (`if`), и часть нитей пошла по одной ветке, а часть по другой, GPU выполнит **обе ветки по очереди**, выключая нити, идущие не туда. Это называется дивергенцией warp'а. Ветвистый код на GPU не ускоряется, а деградирует; хорошая GPU-программа — та, где 32 соседние нити делают одно и то же.

### Иерархия памяти

Память GPU устроена ступеньками, разница между ними — порядки:

* **Регистры**, отведённые каждой нити свои, доступ за ~1 такт. Локальные переменные, объявленные в ядре-функции (kernel, определение ниже), живут здесь.
* **Разделяемая память (shared memory)**, общая для блока нитей, около 100 КБ, приходящихся на мультипроцессор, доступ за ~10–30 тактов. Это кеш, управляемый вручную: сюда заранее загружают кусок данных, читаемый блоком многократно.
* **Глобальная память**, гигабайты с коробки видеокарты. Видна всем нитям, полоса огромная (сотни ГБ/с), но латентность доходит до сотен тактов.

GPU прячет латентность глобальной памяти не кешами, как CPU, а числом запущенных нитей. Пока один warp ждёт данные из памяти, мультипроцессор исполняет другие. Поэтому нитей запускают сильно больше, чем физических ядер: десятки тысяч и миллионы здесь нормальны.

## Модель CUDA

CUDA — платформа NVIDIA для вычислений общего назначения на GPU. Её терминология используется во всех инструментах для GPU.

* **Host** объединяет CPU и оперативную память, а **Device** объединяет GPU и его память. У них разные адресные пространства; данные из одного надо явно копировать в другой.
* **Ядром (kernel)** называют функцию, которую host отправляет на исполнение в device. Она исполняется одновременно тысячами нитей, и каждая нить выполняет один и тот же код, но обрабатывает доставшийся ей элемент данных.
* Нити организованы в двухуровневую иерархию: **сетка (grid) → блоки (blocks) → нити (threads)**.

```text
Grid (сетка — весь запуск ядра)
├── Block 0 ── [нить 0][нить 1] ... [нить 255]
├── Block 1 ── [нить 0][нить 1] ... [нить 255]
├── Block 2 ── [нить 0][нить 1] ... [нить 255]
└── ...

глобальный индекс нити = blockIdx.x * blockDim.x + threadIdx.x
```

Блок целиком попадает на один мультипроцессор, поэтому его нити могут общаться через разделяемую память и синхронизироваться между собой. Блоки же друг о друге ничего не знают, и планировщик раскидывает блоки по свободным мультипроцессорам как угодно. Поэтому одна и та же программа масштабируется и на ноутбучную видеокарту с 20 мультипроцессорами, и на серверную со 130.

Внутри ядра нить первым делом определяет свой индекс. У неё есть номер блока `blockIdx`, размер блока `blockDim` и номер внутри блока `threadIdx`. Глобальный индекс собирается из этих трёх чисел, которые раздаёт среда исполнения.

```text
i = blockIdx.x * blockDim.x + threadIdx.x
```

Например, нить номер 5 в блоке номер 3 при блоках по 256 нитей получит `i = 3 * 256 + 5 = 773` и будет обрабатывать 773-й элемент. Цикл `for i in range(n)`, привычный по CPU-коду, на GPU исчезает: вместо него запускается `n` нитей, и каждая делает одну итерацию.

## Главное правило: данные должны жить на GPU

У GPU своя память, и соединена она с host'ом шиной PCIe, дающей полосу порядка 10–30 ГБ/с. Полоса памяти самого GPU — около терабайта в секунду. Копирование массива host → device часто стоит дороже всех вычислений над ним. Насколько дороже, решает количество арифметики, приходящейся на каждый переданный байт.

Возьмём гигабайт данных на host'е. Пересылка через PCIe займёт около 50 мс. Поэлементная операция вроде \\(y = 2x\\) прочитает и запишет два гигабайта по внутренней полосе GPU и уложится в 2 мс. Счёт в двадцать пять раз дешевле пересылки, и гонять массив туда-сюда бессмысленно. Умножение матриц — противоположный случай. Гигабайт `float32` — это матрица \\(16384 \times 16384\\), её умножение требует \\(2n^3 \approx 8{,}8\\) терафлоп и занимает сотни миллисекунд даже на быстрой карте, то есть на порядок дороже пересылки.

Разница в том, что умножение матриц делает \\(O(n^3)\\) работы над \\(O(n^2)\\) данных, а поэлементная операция делает \\(O(n)\\) работы над \\(O(n)\\) данных. Чем выше отношение работы к данным, тем легче окупается копирование в начале расчёта.

Отсюда антипаттерн номер один:

```text
плохо:  [CPU: данные] → GPU → шаг → [CPU] → GPU → шаг → [CPU] → ...
хорошо: [CPU: данные] → GPU → шаг → шаг → шаг → ... → [CPU: результат]
```

Правильная схема: скопировать входные данные на устройство **один раз**, выполнить там всю цепочку вычислений (все шаги по времени, все итерации) и забрать назад только результат, а лучше диагностику, посчитанную прямо на карте: энергию, спектр, картинку. Если в цикле по шагам есть копирование туда-обратно, ускорения не будет.

## CuPy: NumPy на видеокарте

Самый короткий путь к GPU из Python — [CuPy](https://cupy.dev/). Это реализация интерфейса NumPy поверх CUDA, дающая те же `ndarray`, `sum`, `dot`, `fft`, `linalg`, только массивы лежат в памяти видеокарты, а операции над ними выполняет GPU.

```python
import cupy as cp

x = cp.arange(10**7, dtype=cp.float32)   # массив рождается сразу в памяти GPU
y = cp.sin(x) ** 2 + cp.cos(x) ** 2      # считает GPU, host только раздаёт команды
s = y.sum()                              # редукция тоже на GPU, результат — 0-мерный массив

y_host = cp.asnumpy(y)                   # явное копирование device → host (в NumPy-массив)
x_gpu = cp.asarray(y_host)               # и обратно, host → device
```

Если ты умеешь писать векторизованный NumPy-код, ты уже умеешь программировать GPU. В большинстве скриптов достаточно заменить `import numpy as np` на `import cupy as cp`.

Проверим на умножении матриц.

```python
import numpy as np
import cupy as cp
from time import perf_counter

n = 4096
A = np.random.rand(n, n).astype(np.float32)
B = np.random.rand(n, n).astype(np.float32)

# --- CPU ---
t0 = perf_counter()
C = A @ B
t_cpu = perf_counter() - t0

# --- GPU ---
A_gpu = cp.asarray(A)                  # копируем данные на видеокарту один раз
B_gpu = cp.asarray(B)

C_gpu = A_gpu @ B_gpu                  # прогрев: первый вызов компилирует ядра
cp.cuda.Stream.null.synchronize()

t0 = perf_counter()
C_gpu = A_gpu @ B_gpu
cp.cuda.Stream.null.synchronize()      # дожидаемся, пока GPU реально досчитает
t_gpu = perf_counter() - t0

print(f"CPU: {t_cpu:.3f} c, GPU: {t_gpu:.4f} c, ускорение x{t_cpu / t_gpu:.0f}")
```

На бесплатной T4, выданной в Colab, это даёт ускорение в один-два порядка относительно NumPy, притом что сам NumPy уже упирается в предел процессора.

Два замечания про замеры на карте:

* **Запуск ядер асинхронный.** Вызов `A_gpu @ B_gpu` ставит работу в очередь GPU и возвращается немедленно. Если замерить время без `cp.cuda.Stream.null.synchronize()`, получатся микросекунды — время постановки в очередь, а не вычислений. Синхронизация происходит и неявно, при копировании результата на host или вызове `float(s)`, поэтому обычный код работает корректно; в бенчмарках синхронизируй явно.
* **Первый вызов уходит на прогрев.** При первом обращении CuPy компилирует ядра под конкретную видеокарту, на это уходят доли секунды. Замеряй со второго раза (как и у Numba).

Функция `cp.get_array_module(x)` возвращает `numpy` или `cupy` в зависимости от того, где лежит массив `x`. Так пишут библиотечные функции, одинаково работающие и на CPU, и на GPU.

## Numba CUDA: пишем ядро сами

CuPy покрывает всё, что выражается операциями над целыми массивами. Иногда алгоритм в них не укладывается: нестандартная поэлементная логика или свой обход данных. В главе про профилирование мы в такой ситуации вешали `@numba.jit` на функцию с циклами. У Numba есть и второй бэкенд: декоратор `@cuda.jit` компилирует Python-функцию в CUDA-ядро.

Канонический пример — сложение векторов.

```python
import numpy as np
from numba import cuda

@cuda.jit
def add_kernel(a, b, out):
    i = cuda.grid(1)              # глобальный индекс нити в одномерной сетке
    if i < out.size:              # нитей запущено чуть больше, чем элементов
        out[i] = a[i] + b[i]      # каждая нить обрабатывает ровно один элемент

n = 10_000_000
a = np.random.rand(n).astype(np.float32)
b = np.random.rand(n).astype(np.float32)

# явно переносим данные на device и заводим там массив под результат
d_a = cuda.to_device(a)
d_b = cuda.to_device(b)
d_out = cuda.device_array_like(d_a)

# конфигурация запуска: сколько нитей в блоке и сколько блоков в сетке
threads_per_block = 256
blocks_per_grid = (n + threads_per_block - 1) // threads_per_block  # округление вверх

add_kernel[blocks_per_grid, threads_per_block](d_a, d_b, d_out)
cuda.synchronize()                # дожидаемся завершения (запуск, как всегда, асинхронный)

out = d_out.copy_to_host()        # забираем результат на CPU
```

Разберём по шагам:

* **Тело ядра** содержит код *одной* нити. Циклов по элементам нет: параллелизм создаётся миллионами запущенных нитей. `cuda.grid(1)` — сокращение для `cuda.blockIdx.x * cuda.blockDim.x + cuda.threadIdx.x`, формулы глобального индекса.
* **Проверка `if i < out.size`** обязательна. Число запущенных нитей кратно размеру блока, поэтому для `n = 10^7` при блоках по 256 запустится 39 063 блока, то есть 10 000 128 нитей, на 128 больше, чем элементов. Лишние нити без проверки полезли бы за границу массива.
* **`threads_per_block`** обычно берут 128–512 (максимум 1024, лучше кратно 32, размеру warp'а). Точное значение подбирают замерами; для начала 256 — хороший выбор.
* **`blocks_per_grid`** вычисляется из размера задачи: классическая формула округления вверх `(n + tpb - 1) // tpb`.
* **Конфигурация в квадратных скобках** `kernel[blocks, threads](...)` сообщает CUDA через Numba, сколько нитей запустить.
* **Ядро ничего не возвращает**, а умеет только писать в переданные ему массивы, поэтому `d_out` создаём заранее.

Если передать в ядро обычные NumPy-массивы, Numba скопирует их на GPU и обратно сама, что удобно для первых проб, но в цикле по шагам это антипаттерн с копированием. Явные `cuda.to_device` / `copy_to_host` держат трафик через PCIe под контролем. Ядра Numba принимают и массивы CuPy.

Внутри `@cuda.jit`-функции доступно урезанное подмножество Python: числа, арифметика, циклы, условия, обращение к массивам, математика из `math`. Никаких списков, словарей и создания массивов, как и в `nopython`-режиме обычной Numba, только строже.

Сетки и блоки бывают не только одномерными. Для матриц, изображений с детекторов и разностных сеток удобны двумерные: нить получает пару индексов и обрабатывает свой узел. Ядро, считающее дискретный лапласиан для уравнений теплопроводности и Пуассона:

```python
@cuda.jit
def laplace_kernel(u, out):
    i, j = cuda.grid(2)                   # у нити теперь два индекса: строка и столбец
    if 0 < i < u.shape[0] - 1 and 0 < j < u.shape[1] - 1:   # только внутренние узлы
        out[i, j] = (u[i + 1, j] + u[i - 1, j] +
                     u[i, j + 1] + u[i, j - 1] - 4 * u[i, j])

threads_2d = (16, 16)                     # блок 16x16 = 256 нитей
blocks_2d = ((nx + 15) // 16, (ny + 15) // 16)   # покрываем сетку nx на ny узлов
laplace_kernel[blocks_2d, threads_2d](d_u, d_lap)
```

Каждая нить читает пять соседних узлов и пишет один, а GPU повторяет это для всех узлов сетки. Явная разностная схема для двумерной теплопроводности отсюда в одном шаге: `u += alpha * dt / h**2 * lap`.

## Пример из физики: дрейф частиц в скрещенных полях

Возьмём облако из пяти миллионов электронов в скрещенных полях \\( \vec{E} = (E_0, 0, 0) \\) и \\( \vec{B} = (0, 0, B_0) \\) и проинтегрируем их движение схемой Бориса, стандартной в вычислительной физике плазмы (её родственница была в примере REDPIC). По теории помимо ларморовского вращения облако как целое дрейфует поперёк обоих полей со скоростью \\( E_0 / B_0 \\), не зависящей ни от заряда, ни от массы.

```python
import cupy as cp   # замени на "import numpy as cp" — и тот же код посчитает CPU

# --- параметры задачи (СИ) ---
q, m = -1.602e-19, 9.109e-31          # заряд и масса электрона
E0, B0 = 1e3, 1e-2                    # поля: В/м и Тл
dt, n_steps = 1e-11, 2000             # шаг 10 пс, всего 20 нс (~5 ларморовских периодов)
N = 5_000_000                         # пять миллионов частиц

# --- начальное состояние: облако ~1 мм с тепловым разбросом скоростей ---
# все массивы создаются сразу в памяти GPU и живут там до конца расчёта
rng = cp.random.default_rng(42)
x = rng.standard_normal(N, dtype=cp.float32) * 1e-3    # м
y = rng.standard_normal(N, dtype=cp.float32) * 1e-3
vx = rng.standard_normal(N, dtype=cp.float32) * 1e5    # м/с
vy = rng.standard_normal(N, dtype=cp.float32) * 1e5

# --- константы схемы Бориса: обычные числа, считаются один раз на CPU ---
h = q * dt / (2 * m)                  # q·dt/2m
t = h * B0                            # tan(θ/2) поворота в магнитном поле за шаг
s = 2 * t / (1 + t * t)

for step in range(n_steps):
    vx += h * E0                      # полшага разгона электрическим полем
    px = vx + vy * t                  # поворот скорости вокруг B:
    py = vy - vx * t                  #   промежуточный вектор v'
    vx, vy = vx + py * s, vy - px * s #   точный поворот на угол ω_c·dt
    vx += h * E0                      # ещё полшага разгона
    x += vx * dt                      # сдвигаем частицы
    y += vy * dt

# --- диагностика: на host уходят только два числа, не массивы ---
v_drift = float(y.mean()) / (n_steps * dt)   # float() неявно синхронизирует GPU
energy = float(0.5 * m * (vx**2 + vy**2).mean())
print(f"скорость дрейфа: {v_drift:.3e} м/с (теория: {-E0 / B0:.3e})")
```

Четыре момента:

* **Данные рождаются на GPU** (`cp.random`) и не покидают его все 2000 шагов. На host уходят два числа диагностики, посчитанные там же; только в этот момент host дожидается GPU.
* **Физика умещается в несколько строк массивных операций.** Каждая строка цикла разворачивается в одно-два CUDA-ядра над пятью миллионами элементов. Сам цикл по шагам остаётся на CPU: 2000 итераций дёшевы, дорогая работа идёт внутри.
* **Тот же код работает на CPU.** Поменяв первую строку, получишь NumPy-версию, годную для отладки на ноутбуке без видеокарты. На GPU она побежит в десятки раз быстрее.
* **float32.** Для такой задачи одинарной точности достаточно, а на игровых и облачных картах она в разы быстрее двойной (об этом ниже).

Заготовку можно развивать: неоднородные поля (поле зависит от координаты частицы, но это по-прежнему поэлементные операции), потери и рождение частиц (маски), самосогласованное поле (гистограмма зарядов + Пуассон через `cp.fft`). Всё это остаётся в рамках CuPy.

## Когда GPU не поможет

Ситуации, где GPU бесполезен или вреден:

* **Маленькие данные.** Запуск ядра стоит ~5–10 микросекунд, а копирование через PCIe обходится ещё дороже. Если работы меньше чем на миллисекунду, накладные расходы съедят выигрыш. Массивы из тысячи элементов NumPy сложит быстрее.
* **Ветвистая логика.** Из-за дивергенции warp'ов код, где каждый элемент обрабатывается по-своему (деревья решений, парсинг, сложные `if`-каскады), параллелится плохо.
* **Последовательные зависимости.** Если шаг `i+1` нельзя начать без результата шага `i`, а внутри шага работы мало, параллелить нечего. Одна частица на миллиард шагов остаётся задачей для CPU и Numba. Но миллион *независимых* траекторий по миллиарду шагов — идеальная задача для GPU; в физике часто параллелят по ансамблю или по параметрам, а не по времени.
* **Двойная точность на игровых картах.** GeForce считает float64 в 32–64 раза медленнее float32, так как блоки FP64 там почти отсутствуют. Полноценный FP64 (половина от FP32) есть только у вычислительных карт вроде A100/H100. Если задаче (небесная механика, длинное интегрирование, плохо обусловленная алгебра) нужна двойная точность, замерь её отдельно.
* **Задачи про ожидание, а не про счёт.** Если программа ждёт сеть или диск, смотри главу про асинхронность; GPU не поможет.

Прежде чем переписывать на GPU, профилируй (см. главу про профилирование) и прикинь арифметическую интенсивность, то есть число операций, приходящихся на каждый байт данных. Умножение матриц подходит отлично, а поэлементное сложение уже упирается в память, а не в вычислители.

## Экосистема: не CUDA единой

Писать ядра руками нужно редко. Вокруг CUDA вырос слой библиотек. [PyTorch](https://pytorch.org/) и [JAX](https://docs.jax.dev/) дают NumPy на видеокарте плюс автоматическое дифференцирование и JIT-компиляцию. Физики берут их как вычислительный бэкенд, не только для нейросетей. Перенос тензора на карту умещается в одно `.to("cuda")`, а `jax.jit` и `jax.vmap` компилируют и векторизуют целые модели. Библиотеки [RAPIDS](https://rapids.ai/) (cuDF, cuML) переносят на GPU pandas и scikit-learn, когда узкое место не физика, а обработка таблиц с установки. Под капотом у всех те же ядра, сетки и блоки, поэтому модель CUDA пригодится в любом из них. Если упрёшься в пределы Python — CUDA C++ с теми же концепциями.

## Итог: лестница ускорения

Этой главой раздел про ускорение программ заканчивается. Когда код медленный, иди по ступенькам сверху вниз и останавливайся, как только стало достаточно быстро:

1. **Профилируй.** Пока `line_profiler` не показал, где уходит время, оптимизация на глаз — гадание.
2. **Проверь алгоритм.** Никакое железо не спасёт \\( O(n^2) \\) там, где есть \\( O(n \log n) \\).
3. **Векторизуй.** NumPy вместо циклов даёт обычно первый и самый дешёвый порядок ускорения.
4. **Компилируй.** Numba или Cython — для логики, не уложившейся в массивные операции.
5. **Распараллель на CPU.** Процессы — для счёта (GIL!), асинхронность — когда узкое место ожидание, а не вычисления.
6. **Переноси на GPU.** Однотипную работу над большими массивами — CuPy, свою поэлементную логику — Numba CUDA. Два правила: данные живут на GPU, замеры — с явной синхронизацией.

Тот же векторизованный стиль, разогнавший в начале раздела код на CPU, почти без изменений переносится на видеокарту.
