# Многопоточность и GIL

Следующий шаг после профилирования, векторизации и JIT-компиляции — задействовать все ядра процессора, а не одно. В Python это непросто, и разбираться придётся с самого начала: что такое процесс, что такое поток и почему в Python второе не даёт того, чего от него ждут.

## Необходимый минимум: процессы и потоки

### Процесс

**Процесс** — запущенная программа, и операционная система выделяет каждому процессу собственное, изолированное от остальных состояние:

* виртуальное адресное пространство, то есть своя память, спрятанная от остальных процессов;
* указатель на исполняемую инструкцию;
* стек вызовов;
* системные ресурсы, например открытые файловые дескрипторы.

Несколько задач, которые нужно выполнять одновременно, можно раздать разным процессам. Процессы, разведённые по своим адресным пространствам, не мешают друг другу, но и обмениваться данными им сложно: общей памяти у них нет.

### Поток

**Поток** исполняется независимо от других потоков, как и процесс, но живёт *внутри* процесса и делит с ним адресное пространство и системные ресурсы. Двум потокам одного процесса ничего не стоит работать с общими данными, поскольку они видят одни и те же объекты, размещённые в общей памяти.

Удобно это до тех пор, пока два потока не полезут в одни данные одновременно: тогда начинаются гонки, о которых ниже.

Порядком исполнения и процессов, и потоков распоряжается операционная система, поочерёдно выдающая каждому по нескольку тактов процессора.

## Модуль `threading`

Поток в Python — обычный системный поток, и управляет его исполнением операционная система, а не интерпретатор. Создать поток можно классом `Thread`, объявленным в модуле стандартной библиотеки `threading`.


```python
import time
from threading import Thread

def countdown(n):
    for i in range(n):
        print(n - i - 1, "left")
        time.sleep(1)
```


```python
t = Thread(target=countdown, args=(3,))
```


```python
t.start()
```

    2 left
    1 left
    0 left


Другой способ создать поток — наследование.


```python
class CountdownThread(Thread):
    def __init__(self, n):
        super().__init__()
        self.n = n
        
    def run(self): # вызывается методом start
        for i in range(self.n):
            print(self.n - i - 1, "left")
            time.sleep(1)
```


```python
t = CountdownThread(3)
```


```python
t.start()
```

    2 left
    1 left
    0 left


Этот подход ограничивает переиспользование кода: функциональность, заключённая в класс `CountdownThread`, доступна только в отдельном потоке.

Встроенного способа убить поток в Python нет, и это осознанное решение. Корректное завершение почти всегда означает освобождение ресурсов: поток мог открыть файл, дескриптор которого надо закрыть, или захватить примитив синхронизации, который надо отпустить. Убийство на полуслове оставило бы всё это висеть, поэтому о завершении поток просят флагом, выставленным снаружи.


```python
class Task:
    def __init__(self):
        self._running = True
    
    def terminate(self):
        self._running = False
    
    def run(self, n):
        while self._running:
            ...
```

Набор примитивов синхронизации в модуле `threading` стандартный:
* `Lock`, обычный мьютекс, дающий эксклюзивный доступ к разделяемому состоянию.
* `RLock`, рекурсивный мьютекс, разрешающий потоку, владеющему мьютексом, захватывать его больше одного раза.
* `Semaphore`, вариация мьютекса, захватываемая не более фиксированного числа раз.
* `BoundedSemaphore`, семафор, следящий за тем, чтобы его захватывали и освобождали одинаковое число раз.

Все примитивы синхронизации реализуют единый интерфейс:
* метод `acquire` захватывает примитив синхронизации,
* а метод `release` освобождает его.


```python
from threading import Lock


class SharedCounter:
    def __init__(self, value):
        self._value = value
        self._lock = Lock()
    
    def increment(self, delta=1):
        self._lock.acquire()
        self._value += delta
        self._lock.release()
    
    def get(self):
        return self._value
```

## Модуль `queue`

Обмениваться данными между потоками, расставляя мьютексы руками, неудобно. Обычно берут готовую очередь; модуль `queue` реализует несколько потокобезопасных вариантов.

* `Queue`, очередь FIFO,
* `LifoQueue`, очередь LIFO, то есть стек,
* `PriorityQueue`, очередь с приоритетом: элементы, обычно пары (priority, item), выдаются не в порядке поступления, а по возрастанию приоритета.

Все методы, меняющие состояние, работают под мьютексом. `Queue` держит элементы в `deque`, а `LifoQueue` и `PriorityQueue` — в обычном списке, защищённом тем же мьютексом.

Классическая схема «производитель-потребитель» на очереди выглядит так.


```python
def worker(q):
    while True:
        item = q.get() # блокирующе ждёт следующий
        do_something(item) # элемент
        q.task_done() # уведомляет очередь о выполнении
        
def master(q):
    for item in source():
        q.put(item)

    # блокирующе ждёт, пока все элементы
    # очереди не будут обработаны
    q.join()
```

## Пример с модулем `futures`: `integrate`

Проверим это на счётной задаче: численное интегрирование методом прямоугольников, циклом по заданному разбиению отрезка.


```python
import math

def integrate(f, a, b, *, n_iter=1000):
    acc = 0
    step = (b - a) / n_iter
    for i in range(n_iter):
        acc += f(a + i * step) * step
    return acc
```


```python
integrate(math.cos, 0, math.pi / 2)
```




    1.0007851925466296




```python
from functools import partial

def integrate_async(f, a, b, *, n_jobs, n_iter=1000):
    executor = ThreadPoolExecutor(max_workers=n_jobs)
    spawn = partial(executor.submit, integrate, f,
                    n_iter=n_iter // n_jobs)
    step = (b-a)/n_jobs
    fs=[spawn(a+i*step,a+(i+1)*step)
        for i in range(n_jobs)]
    return sum(f.result() for f in as_completed(fs))
```


```python
integrate_async(math.cos, 0, math.pi / 2, n_jobs=2)
```




    1.0007851925466305

### Вот он, GIL

Два потока вместо одного дали выигрыш в проценты вместо ожидаемого ускорения вдвое. Причина — **GIL** (global interpreter lock, глобальная блокировка интерпретатора).

GIL — мьютекс, гарантирующий, что в каждый момент времени байт-код исполняет только один поток. Внутреннее состояние интерпретатора (в первую очередь счётчики ссылок у каждого объекта) не защищено от одновременного доступа, и глобальная блокировка — самый простой способ не дать двум потокам испортить его разом. Плата за простоту — результат замера выше.

Следствие: **в обычной сборке CPython потоки не ускоряют вычисления.** Сколько бы их ни было, байт-код исполняется по очереди, а к вычислениям добавляются накладные расходы на переключение, делающие многопоточную версию иногда даже медленнее однопоточной.

### Когда GIL мешает, а когда нет

Мешает ли GIL, зависит от того, чем занята программа.

Если она **считает**, потоки бесполезны. Обойти GIL можно двумя путями: уйти в отдельные процессы, у каждого из которых свой интерпретатор со своим GIL (об этом ниже), или спуститься в скомпилированный код, умеющий GIL отпускать.

Если программа **ждёт**, то есть читает файл, тянет данные по сети, опрашивает прибор, на время ожидания поток отпускает GIL, и остальные работают. Для такой нагрузки потоки подходят, и проигрыша от блокировки нет.

NumPy на длинных операциях тоже отпускает GIL: пока перемножаются большие матрицы, интерпретатор свободен для остальных потоков. Поэтому многопоточность в связке с NumPy работает лучше, чем можно ожидать.

Оговорка «в обычной сборке CPython» существенна. Начиная с 3.13 интерпретатор собирается и вовсе без глобальной блокировки (PEP 703): такая сборка ставится рядом с обычной и зовётся `python3.13t`, а с 3.14 режим свободных потоков официально поддержан (PEP 779), и потоки в нём считают параллельно, без процессов и без Cython. Плата — 5–10 %, потерянные на однопоточном коде, и неготовность части C-расширений, писавшихся в расчёте на то, что блокировка прикроет их сама. Узнать, в какой сборке ты работаешь, позволяет `sys._is_gil_enabled()`, возвращающий `False` в свободнопоточной. Пока она не стала умолчанием, всё сказанное в этой главе относится к обычной.

### C и Cython: как отпустить GIL

Скомпилированный код может отпустить GIL явно, на то время, пока он не трогает объекты Python. В Cython для этого есть блок `with nogil`, внутри которого живут только сишные типы, зато остальные потоки работают параллельно.


```python
%load_ext Cython
```


```cython
%%cython

from libc.math cimport cos

def integrate(f, double a, double b, long n_iter):
    cdef double acc = 0
    cdef double step=(b-a)/n_iter
    cdef long i
    with nogil:
        for i in range(n_iter):
            acc += cos(a + i * step) * step
    return acc
```

Первый аргумент здесь оставлен только ради совместимости с `integrate_async`, а сама функция зашита под `cos`: вызвать питоновский `f` внутри `with nogil` нельзя.


```python
%%timeit -n100
integrate_async(math.cos, 0, math.pi / 2, n_iter=10**6, n_jobs=2)
```

    5.88 ms ± 126 µs per loop (mean ± std. dev. of 7 runs, 100 loops each)


Те же два потока, тот же `integrate_async`, и 5.88 мс вместо 142. Выигрыш этот составной. Потоков два, поэтому на снятие GIL приходится не больше двух раз; остальное, примерно двенадцатикратное, дала компиляция в машинный код. Вывод: сначала Cython, и только потом распараллеливание уже скомпилированного кода.

> **О замерах ниже.** Ячейка выше переопределила имя `integrate`: теперь под ним живёт скомпилированная Cython-версия. Замеры двух следующих разделов — про процессы и про `joblib` — сняты не с ней, а с исходной, чистой Python-версией в свежем ядре; чтобы их повторить, перезапусти блокнот, пропустив ячейку с `%%cython`. Иначе Cython-функцию отдать в пул процессов и вовсе не выйдет: она живёт в модуле `_cython_magic_<hash>` из `~/.ipython/cython`, который не лежит на `sys.path`.

## Модуль `multiprocessing`
### Процессы как ещё одно лекарство от GIL

Раз глобальная блокировка одна на интерпретатор, самый прямой способ её обойти — завести несколько интерпретаторов. Это и делают процессы: у каждого свой GIL, друг другу они не мешают, и на восьми ядрах восемь процессов считают одновременно.

Плата — изоляция. Процессы не разделяют память, поэтому всё, что нужно передать между ними, приходится сериализовать и копировать. Для расчёта, где каждому процессу отдают кусок работы и забирают число, это несущественно; для задачи с большим общим состоянием накладные расходы на пересылку могут съесть весь выигрыш.

За работу с процессами отвечает модуль `multiprocessing`, устроенный похоже на `threading`.


```python
import multiprocessing as mp
```


```python
p = mp.Process(target=countdown, args=(5, ))
```


```python
p.start()
```

    4 left
    3 left
    2 left
    1 left
    0 left


Примитивы синхронизации те же: мьютексы, семафоры, условные переменные. Для обмена данными между процессами есть `Pipe`, соединение двух процессов поверх сокетов.


```python
def ponger(conn):
    conn.send("pong")
```


```python

p = mp.Process(target=ponger, args=(child_conn, ))
```


```python

```


## Процессы и производительность

Реализация `integrate_async` на пуле потоков работала долго; попробуем пул процессов.


```python
from concurrent.futures import ProcessPoolExecutor
```


```python
def integrate_async(executor, f, a, b, *, n_jobs, n_iter=1000):
    spawn = partial(executor.submit, integrate, f,
                    n_iter=n_iter // n_jobs)

    step = (b - a) / n_jobs
    fs=[spawn(a + i * step, a + (i + 1) * step)
        for i in range(n_jobs)]

    return sum(f.result() for f in as_completed(fs))
```

Пул принимается аргументом, а не создаётся внутри. Запуск
процесса стоит десятки миллисекунд: на macOS и Windows интерпретатор стартует
заново, целиком, а начиная с Python 3.14 и на Linux место `fork` занял
`forkserver`, форкающий процессы от отдельного чистого сервера. Наследования
всего состояния родителя больше нет нигде, поэтому и функция, которую передают
в пул, должна лежать в импортируемом модуле, а не в ячейке блокнота. Пул,
созданный внутри измеряемой функции, превратит замер счёта в замер запуска интерпретатора.
Вдобавок `ProcessPoolExecutor`, брошенный без закрытия, оставляет процессы жить,
и за сотню итераций `%%timeit` машина обрастёт ими.

```python
with ProcessPoolExecutor(max_workers=2) as executor:
    integrate_async(executor, math.cos, 0, math.pi / 2,
                    n_iter=10**6, n_jobs=2)          # прогрев
    %timeit -n5 integrate_async(executor, math.cos, 0, math.pi / 2, \
                                n_iter=10**6, n_jobs=2)
```

    21 ms ± 0.2 ms per loop (mean ± std. dev. of 5 runs, 5 loops each)

В этом же прогоне последовательный счёт занимает 44 мс, а два процесса дают 21 мс,
то есть двукратное ускорение на паре ядер: у каждого процесса свой GIL.
С числами из разделов выше эту пару не сопоставляй: она снята отдельно.


## Пакет `joblib`

Пакет `joblib` даёт параллельный аналог цикла `for` для независимых итераций, которые надо разложить по ядрам. Потоками или процессами — задаётся аргументом `backend` конструктора.


Замеры ниже сделаны на **исходной**, чистой Python-версии `integrate`. Если в блокноте
уже выполнена ячейка с `%%cython`, имя `integrate` указывает на скомпилированную
функцию, и числа получатся на порядок меньше. Сравнивать их с тем, что было
до Cython, нельзя; чтобы повторить замеры отсюда, определи `integrate` заново.

```python
from joblib import Parallel, delayed

def integrate_async(f, a, b, *, n_jobs, n_iter=1000, backend=None):
    step = (b - a) / n_jobs
    with Parallel(n_jobs=n_jobs, backend=backend) as parallel:
        fs = (delayed(integrate)(f, a + i * step,
                                 a + (i + 1) * step,
                                 n_iter=n_iter // n_jobs)
              for i in range(n_jobs))
        return sum(parallel(fs))   # внутри with: пул переиспользуется
```


```python
%%timeit -n100
integrate_async(math.cos, 0, math.pi / 2, n_iter=10**6, n_jobs=2, backend="threading")
```

    104 ms ± 280 µs per loop (mean ± std. dev. of 7 runs, 100 loops each)



```python
%%timeit -n100
integrate_async(math.cos, 0, math.pi / 2, n_iter=10**6, n_jobs=2, backend="multiprocessing")
```

    290 ms ± 1.13 ms per loop (mean ± std. dev. of 7 runs, 100 loops each)


Сам по себе `joblib` ничего не ускоряет, он раскладывает работу, а упрётся она в тот же GIL на потоках или в ту же сериализацию на процессах.

## JIT-компилятор `numba`

Numba из главы [«Скорость выполнения программ»](./perf.md) обходит GIL заодно с ускорением: декоратор `@jit(nopython=True, parallel=True)` компилирует функцию в машинный код, отпускающий блокировку, после чего цикл `prange` раскладывается по ядрам.


```python
import math
from numba import jit, prange

@jit(nopython=True, parallel=True, fastmath=True)
def integrate(a, b, n_iter=1000):
    acc = 0
    step = (b - a) / n_iter
    for i in prange(n_iter):
        acc += math.cos(a + i * step) * step
    return acc
```


```python
%%timeit -n100
integrate(0, math.pi / 2, n_iter=10**6)
```

    5.11 ms ± 983 µs per loop (mean ± std. dev. of 7 runs, 100 loops each)


## Резюме

Перед выбором инструмента задай один вопрос: **программа считает или ждёт?**

Если ждёт сети, диска, прибора, ответа пользователя, бери потоки. GIL на время ожидания отпускается, потоки дёшевы, и десятки ожиданий, висящих разом, обходятся почти бесплатно. Если ждать предстоит тысячами, переходи к асинхронности из следующей главы.

Если считает, потоки в обычной сборке CPython не помогут, сколько бы их ни было. Три пути: вынести расчёт в отдельные процессы через `multiprocessing`, где у каждого свой интерпретатор и свой GIL; спуститься в скомпилированный код на Cython или C, умеющий GIL отпускать; или, что обычно проще всего, поручить расчёт NumPy, отпускающему блокировку за тебя.

Прежде чем распараллеливать, **замерь**. Часто узкое место не там, где казалось, и одна правка алгоритма даёт больше, чем любое количество потоков.
