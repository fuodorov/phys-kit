# Инструментарий

Инструменты меняются каждые несколько месяцев, поэтому важнее запомнить не названия, а **три формы**, в которых ИИ приходит в разработку.

## Три формы инструментов

Первая, самая простая для входа, — плагин к редактору. Он ставится в привычную тебе среду (VS Code, JetBrains, Neovim) и живёт внутри неё, ничего не ломая. Самый известный — GitHub Copilot; бесплатный тариф у него есть для всех, а у студентов бесплатен полный, о чём подробнее в следующей главе.

Вторая форма — редактор, спроектированный вокруг ассистента: отдельная среда разработки, где модель видит проект целиком, а не только открытый файл. Большинство таких редакторов выросло из VS Code, поэтому переход почти не требует привыкания, а настройки и расширения переносятся. Примеры — Cursor и Windsurf.

Третья форма — терминальный агент, работающий в командной строке в каталоге твоего проекта. Он читает файлы, правит их, запускает тесты и разбирает вывод. Эта форма лучше остальных подходит для больших проектов и удалённых машин без графики — обычная ситуация для физика, работающего на кластере по SSH. Так работают Claude Code, Aider и Gemini CLI.

Границы между формами размываются: редакторы обзаводятся агентным режимом, а терминальные агенты, выросшие из простых скриптов, получают интеграцию с IDE. Выбирай по тому, где ты работаешь.

## Что эти инструменты умеют

Набор возможностей у всех примерно одинаковый, различается глубина вмешательства в код:

* **Автодополнение.** Модель предлагает продолжение по ходу набора. Подсказка серым текстом выглядит правдоподобно, и её легко принять не глядя.
* **Правка выделенного.** Выделяешь кусок кода и говоришь, что с ним сделать, например «добавь обработку ошибок», «перепиши через генератор», «векторизуй этот цикл».
* **Чат по проекту.** Диалог, позволяющий сослаться на файлы. Хорош для вопроса «почему это падает» с приложенным трейсбеком.
* **Агентный режим.** Ставишь задачу целиком, а агент сам читает нужные файлы, вносит правки, запускает тесты и исправляется по упавшим.

Чем ниже по этому списку, тем больше инструмент делает сам, тем меньше у тебя контроля и тем внимательнее нужно проверять результат.

## Правила проекта

Все зрелые инструменты читают из репозитория файл с правилами, описывающий, как принято писать код в проекте. Агент подмешивает его в каждый запрос, и повторять одно и то же не приходится.

Сюда записывают договорённости, принятые в группе:

```text
- Код на Python 3.12, стиль — PEP 8, длина строки 79 символов.
- Единицы СИ везде, кроме энергии частиц: она в МэВ.
- Массивы обрабатываем векторизованно, циклов по элементам не пишем.
- Новый код сопровождается тестом в tests/.
- Данные экспериментов в репозиторий не коммитим.
```

Парный механизм — файл игнорирования по образцу `.gitignore`. В него заносят всё, что не должно уезжать в модель: файлы с паролями и токенами, персональные данные, ещё не опубликованные сырые данные экспериментов и материалы, закрытые соглашением с институтом. Отправленное вернуть нельзя, а утёкший токен придётся перевыпускать.

## MCP: как подключить агенту свои инструменты

**Model Context Protocol (MCP)** — открытый протокол, предложенный Anthropic в конце 2024 года и подхваченный остальными.

Инструментов, нужных агенту, много: база данных, система управления задачами, архив системы управления установкой и документация, разложенная по вики. Клиентов, которым такой доступ нужен, тоже много. Без общего протокола пришлось бы писать интеграцию для каждой пары «клиент — инструмент», а число таких пар растёт как произведение двух растущих списков. MCP вводит единый интерфейс: инструмент, написанный один раз в виде MCP-сервера, доступен любому клиенту, поддерживающему протокол.

Сценарий для научной группы: поднять MCP-сервер, смотрящий в архив телеметрии установки, и спрашивать у агента, что происходило с током в магнитах в ночь неудачного запуска, вместо того чтобы каждый раз писать разбор логов заново.

## Как не наделать бед

Несколько правил; заведи их с первого дня работы с агентами:

1. **Только под контролем версий.** Всё, сделанное агентом, должно быть видно в `git diff` и откатываться одной командой; про [Git](../dev/git.md) речь пойдёт в конце этой части.
2. **Читай перед принятием.** Отказаться от непонятной правки дешевле, чем потом искать в ней ошибку.
3. **Мелкими шагами.** Задача «перепиши мне весь модуль» даёт результат, который не вычитать в разумное время. Задача «вынеси этот кусок в функцию и добавь тест» проверяется легко.
4. **Не давай запускать разрушительные команды.** Удаление файлов, `git push` и отправка чего-либо наружу остаются решением, принимаемым тобой, а не агентом.
5. **Ответственность на тебе.** Автором кода считается человек, поставивший под ним коммит. Ссылка на то, что «так предложил ассистент», не работает ни в ревью, ни в статье.
